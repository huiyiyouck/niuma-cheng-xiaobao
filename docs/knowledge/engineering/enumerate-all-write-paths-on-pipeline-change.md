# 链路改造必须先枚举全部写入路径

> 来源：v0.6.1 关闭检查发现 x-stream-manager 漏改（2026-07-27）

## 教训

v0.6.1 把「抓取入库 → 处理」链路改造为 direct/ai 分流 + task 队列模式。改造覆盖了 `dispatcher.ts` 的定时抓取入库路径，但**漏掉了 `x-stream-manager.ts` 的实时推送入库路径**——它独立 INSERT `raw_items`（吃列默认值 `process_type='ai'`）并硬建旧式 `process` task，导致条目绕开新链路走旧逻辑，`l1_status` 永停 `not_started`，前端显示「待解析」但实际已处理完。

**四轮 Review（PRD 三方 / 设计三方 / 实现 R1 三方 / R3-R4 三方）均未抓住**：所有人都顺着被改的文件看，没人反向问「这张表还有谁在写？」。潜伏原因：X Stream 恰好断流，生产零显现，verify SQL 0 行反而佐证了「没问题」。

## 规则

改造任何「数据入口 → 状态机」链路时，第一步先做**写入路径普查**并写进设计文档：

```bash
# 以目标表为锚点反查所有写入者（而不是顺着改动文件看）
grep -rn "INSERT INTO raw_items\|insert(rawItems" server/src/
```

- 设计文档必须列出「本表全部写入点 × 本次是否适配」对照表，Review 方逐行核对。
- 定时任务、实时流、回填脚本、管理接口是最容易被遗漏的四类旁路写入者。
- 「生产没显现」不等于「没问题」——数据源恰好静默会掩盖旁路缺陷，verify SQL 须注明其结论的适用前提。

## 适用场景

- 新增/变更状态机字段、分流字段（如 process_type）
- 表结构语义变更（某列从「可空」变「必须由特定逻辑写入」）
- 双写迁移、灰度切换
