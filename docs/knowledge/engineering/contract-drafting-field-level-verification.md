# 跨项目契约起草：字段表禁止凭记忆写，逐字段对照真源

> 来源：REQ-003 `news-l1-db` 契约两次笔误订正（O-1 / C-10，2026-07-25 ~ 27）

## 教训

`news-l1-db` 数据库边界契约 v1 由 PM 起草，两处字段级内容**凭记忆书写**，均与既有真源相反：

1. **O-1**：职责边界表写「`score_total` 由 ai 写入」——而 HTTP 契约 / ai 业务边界 / xiaobao 代码（`calcScoreTotal`）三处真源一致为「归 xiaobao」。
2. **C-10**：`tags_v2` 第五类写成 `sentiment`——HTTP 契约真源是 `processing`，且 xiaobao 前后端 `sentiment` 零消费、ai 从不产出。

两次都不是 xiaobao 侧 Review 抓出的，而是 **ai 侧承接后逐字段核对代码基线时发现**，每次都升级成「P0 契约冲突」流程（提问 → 核查 → 订正 → CHANGELOG → 版本号递增），消耗双侧多轮往返。

## 规则

- 契约里的字段表、枚举表、职责边界表，每一行都必须**指向一个可核查的真源**（schema 定义 / 既有契约行号 / 代码行号），起草时逐行对照，不允许「我记得是这样」。
- 已有并行契约（如 HTTP 模式）时，先明确「语义以谁为准」的裁决条款（本例为变更纪律第 5 条），起草新契约时把旧契约字段表**并排打开**逐字段抄，而非默写。
- 契约出稿前的自检清单加一项：`grep` 关键字段名在两侧代码库的实际使用，零消费/零产出的字段不允许进入契约（要么删掉，要么显式标注「预留，当前无产出方」）。
- 承接方逐字段核对是最后防线，但每漏一次就是一轮 P0 往返——成本远高于起草时的十分钟对照。

## 适用场景

- 新契约起草、契约模式演进（HTTP → DB 等）
- 任何「照着另一份文档写」的场景（PRD 抄需求池、设计抄 PRD 同理）
