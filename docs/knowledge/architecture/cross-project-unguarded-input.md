# 跨项目协作中的「无保障输入」缺陷模式

> 沉淀自 v0.6.1 / REQ-003 与 ai 项目的数据库契约边界协作（2026-07~08）。同一形状的问题在一个迭代内反复出现了五次，值得作为模式记住。

## 症状：一个被依赖的输入，不被任何机制保证

跨项目协作里最难查的不是接口签名对不上——那种问题一调用就报错。真正难的是这一类：

> **一方依赖了另一方的某个值 / 行为 / 端点，但双方都没有任何机制保证它不变、也没有机制在它变化时发出信号。**

它的共同特征：

- **不报错**。变更发生时两侧都正常运行，只是行为悄悄错了；
- **失效方式是"静默降级"**，不是崩溃——表现为质量变差、顺序不对、队列不动、检索为空；
- **归因成本极高**，因为没有任何日志会说"你依赖的那个东西变了"。

## 本迭代出现的五个实例

| # | 被依赖的输入 | 依赖方以为的 | 实际 | 若不发现会怎样 |
|---|-------------|-------------|------|--------------|
| 1 | `AI_STALE_TIMEOUT_MS`（卡死回收窗口） | 1800s（契约起草时臆定，无实现依据） | 600s | ai 三条不变式全建立在不存在的数字上；余量从以为的 4 倍实际只有 1.37 倍 |
| 2 | `tasks.metadata` 列 | 存在（契约写了） | **不存在** | ai 据此推出「关联只能走 jsonb 表达式、会全表扫」的错误结论 |
| 3 | `GRANT UPDATE` 列清单 | 含 `run_after` | **不含** | ai 无法写退避时间 → 失败后立即被重领 → 退避完全失效、几十秒烧完 3 次重试 |
| 4 | `raw_items.l0_label` 的语义 | L0 领域分类结果 | 处理决策标记 | ai 把无信息量的流程标记当领域标签送进 prompt 与 KB 检索 |
| 5 | ai 服务端点 `:8100` | 在跑 | 已停机 31 天 | HTTP 回滚路径指向死端口，且"回滚预案"里没有这一环 |

第 1、5 两条是双方**主动回头核对**才发现的；第 2、3、4 条是对方**逐字段核对契约与实现**时发现的，根因全在我方文档。

## 识别信号

出现下列任一情况，就该怀疑存在无保障输入：

1. **文档里的数字说不出出处**——问"这个 1800s 是怎么来的"答不上来，多半是起草时臆定的；
2. **一方的配置项能单方修改，而另一方的行为依赖它**（env、端口、开关、阈值）；
3. **契约写了"某某由对方保证"，但没写用什么机制保证**；
4. **两个环境（test / prod）的同名配置取值不同，且没人能立刻说清为什么**；
5. **对方的推断听起来合理，但你没核过它依赖的前提**——合理的推断建立在错误的前提上，比明显错误更危险。

## 处置模式：升格为契约参数

发现后不要只改文档里的那个值，要**改变它的权属性质**：

1. **登记进契约**，与表结构、状态枚举同级——不是写在沟通记录或某方的内部文档里；
2. **写明当前值与各环境取值**，以及它约束了对方的什么（最好把不等式 / 依赖关系写出来，将来评估变更时有依据）；
3. **定纪律：任一侧变更前先改契约并通知对方**；
4. **说明后果的对称性**——A 改会怎样、B 改会怎样，两个方向都写，否则容易被当成单方约束。

第 2 步的价值最容易被低估：`AI_STALE_TIMEOUT_MS` 升格时把 ai 的不变式 `N × (预算 + DB上界) < 阈值 × 0.6` 一并写进契约，此后任何一方想调这个值，代入算一下就知道会不会踩到对方，不需要再来回问一轮。

## 配套的个人纪律

这类问题的发现高度依赖核对习惯，本迭代踩出来的三条（已入 `architect-corrections.md`）：

- **对外的每一条代码断言，落笔前按当前 HEAD 重新核实**，跨会话的代码记忆一律作废——多角色并行的仓里，你上一轮登记的"待办"极可能已被别人清掉；
- **`grep | head` 得出的"代码里没有"不算数**，截断会静默丢命中，换命名形态再搜一次；
- **不只核自己要答的那几行，凡引用到的契约段落都要核**——写超时方案时顺手核 `reclaim.ts`，才发现契约那一节有三处与实现不符。

## 什么时候不适用

- **单项目内部配置**不必升格——升格是有成本的（每次改都要走契约流程）。判据是「对方的行为是否依赖它」，不是「它是否重要」；
- **纯实现细节**（内部函数、私有字段）不该进契约，进了反而会把两侧焊死；
- 如果依赖关系是**单向且对方可自愈**的（例如对方有兜底默认值、失效时会明确报错），登记优先级可以降低。
