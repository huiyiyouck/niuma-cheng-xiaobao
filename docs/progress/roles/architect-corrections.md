## 2026-07-28 — 跨会话沿用旧代码记忆，把「已修复」说成「待订正」（同一根因第三次）

- **错误**：答 REQ-003 的 C-5 / C-12 时，直接引用**上一轮会话读到的 `dispatcher.ts` / `l0-classifier.ts` 内容**下断言——「置 queued 与建 task 非同一事务、有毫秒级窗口」「应用层判上限读硬编码常量、不读 `tasks.max_attempts` 列」。而 Developer 已于 2026-07-27 `744d20a` 修复两处（`BEGIN`/`COMMIT` 已加、已改读行内值）。帖子已 push 到 coordination 才复核发现，只能再发一帖更正。
- **根因**：把「上一轮我读过这个文件」当成「我知道它现在是什么样」。**多角色并行的仓里，任何跨会话的代码记忆都是过期的**——Developer / DevOps 会在我两轮答复之间把待办清掉。这与前两条纠错（grep 截断、`l0_label` 语义误判）是同一根因的第三次发作：**没有按当前 HEAD 核实就下断言**。
- **规则**：
  1. **对外答复的每一条代码断言，落笔前按当前 HEAD 重新 grep**，哪怕上一轮刚看过。跨会话记忆一律作废。
  2. 尤其针对**自己上一轮登记为「待办」的项**——它极可能已被其他角色完成。答复前先查该待办的落地状态（`git log`/`INDEX`/代码三选一，不能只凭印象）。
  3. 发帖前做一次「断言清单复核」：把帖子里所有「当前实现是 X」的句子列出来，逐条对当前代码验证一遍再发。
- **修正**：已发更正帖（两处均为「实际比我说的更好」），契约 v1.5 对应两段同步订正。所幸未造成 ai 侧返工，但已是第二次让对方看到我方前后不一致的答复。

## 2026-07-27 — 用 `grep | head` 得出「代码里没有」的结论并写进了跨项目沟通文档

- **错误**：答复 ai 侧 C-3 时用 `grep -rn "score_total" src | grep -v ... | head` 检索，输出被 `head` 截断在 10 行，`l1-processor.ts` 的命中恰好被截掉，据此判定「`score_total` 补算逻辑在代码中根本不存在」，并作为「我方缺口」写进了 coordination 沟通文档。落契约前复核时才发现 `calcScoreTotal` 存在于 `l1-processor.ts:13`。
- **根因**：把「grep 没输出」等同于「代码里没有」。`| head` / `| grep -v` 会静默丢弃命中；驼峰变量名（`scoreTotal`）与 SQL 列名（`score_total`）分处不同行也会让单一模式漏网。**对外上报比对内判断的容错低得多**——契约对方会据此改实现。
- **规则**：
  1. 断言「某功能在代码中不存在」前，必须用**不截断**的检索复核（去掉 `| head`，或先 `| wc -l` 看总数），并至少换一种命名形态再搜一次（下划线 / 驼峰 / 函数名）。
  2. 凡是要写进 coordination（或任何外部可见文档）的「我方缺陷」，**落档前二次核实**，不能只依赖一次检索。
  3. 真实结论往往比「不存在」更精确：本例的准确表述是「函数存在，但只挂在 HTTP 路径上，database 模式无触发点」——**这才是对方需要的信息**，「不存在」既错且没用。
- **修正**：帖子提交前已更正为准确表述（含加权公式），未流出错误结论；契约 v1.3 与 CHANGELOG 均按更正后事实撰写。

## 2026-05-31 — 会话进行中未主动重读 INDEX

- **错误**：本会话内用户两次明确说「你重新读一下 INDEX」，第一次我才发现 DevOps 已经升格了 P2 提案、有 Architect 待办；第二次才发现 Developer 已完成 Step 2、还留了 1 项待我确认。两次都是「以启动时读到的 INDEX 状态为准」，没主动重读。
- **根因**：把 INDEX 当成"启动时读一次的静态文档"，而它实际上是多角色协作中**会被其他角色随时刷新的真源**。多角色异步协作模式下，会话进行中其他角色（Developer、DevOps、PM、Tester、WM）可能刚刚 commit 了新状态。
- **规则**：
  1. 会话**启动时**必读 INDEX
  2. 会话进行中，**每次自己完成一个独立工作单元后**（比如一次 Review、一次决策、一次评估落档）应再次重读 INDEX，确保后续动作基于最新真源
  3. 收到用户提示「再看一下 INDEX」时不要嘴硬"上次刚看过"，直接重读
  4. `git pull --rebase` 失败或返回 `Already up to date` 不等于 INDEX 没变——只有 `cat docs/progress/INDEX.md` 才是真相
- **修正**：本会话两次重读后均补上漏看的待办事项（P2 Step 1 决策 + Step 2 R2 复审），未造成实质损失
- 关联 PM 同类纠错：[pm-corrections.md 2026-05-31](pm-corrections.md)（PM 那条是"以单文档状态字段为准而忽略 INDEX"，本质相同）
