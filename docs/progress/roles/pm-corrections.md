## 2026-08-01 — 任务书越位写操作级细节且未核代码，两点被 DevOps 实机否掉

- **错误**：给 DevOps 写任务书（INDEX 角色待办）时，任务 2 操作栏写了「`AI_INTEGRATION_MODE` 切 database + AI 开关保持关闭」与「`AI_HUB_BASE_URL` 指 8102」。前者**自相矛盾**（`config.ts:96`：mode==='database' 本身就翻开 `aiProcessingEnabled`，切即开，红线不可能守住）；后者跨环境（8102 是 test 专用实例，prod 指它破坏隔离）。DevOps 实机核实后两点均否掉，改用安全解（保持 http + BASE_URL 显空 fail-fast），处置正确。
- **根因**：① PM 越位写了 how——操作方案本是执行角色的域，PM 该给的是目标与红线；② 写 how 时既没核 `config.ts` 也没核实机端口归属，凭对配置项的想当然。
- **纠错**：任务书任务 2 追加认账标注；database 对齐正确归位为「ai v0.2 上生产里程碑」整包事项。
- **规则**：**PM 任务书只写 what（目标）+ 红线（不可越界的约束）+ 验收（怎么算完成），不写操作步骤**；若确需给操作建议，必须先核代码/实机且显式标注「供参考，以执行角色实机核实为准」。执行角色基于实机事实否掉任务书细节时，默认执行角色对。

## 2026-07-26 — 被污染的工具输出当成 Review 证据，产出误报意见 #PM-R3-1

- **错误**：v0.6.1 实现 R3 PM Review 中，指控 `api.ts` 四维评分类型 key 写错（`importance/relevance/credibility`）。R4 时 Developer 用 git 历史核实**指控不成立**——该文件注释从来就是 AD-05 正确四维。
- **根因**：R3 会话中有一轮 grep 工具输出被污染（返回 2000 行重复垃圾）。我当时口头声明了"不拿脏数据当证据"，但污染内容仍残留在上下文里，后续凭记忆引用了它（"api.ts:261-266 确认存在"），未重新用干净命令核实。
- **纠错**：R4 复核时用 `git show <commit>:<file>` 对历史版本定案，公开认账撤回意见。
- **规则**：**工具输出出现异常（截断错乱、超量重复、与预期结构不符）后，该轮及其派生的一切"事实"全部作废**；写进 Review 意见前必须用干净命令（git show / 重新 Read）逐条重新取证。Review 意见的每一条都要能指到当次会话内一次干净的取证输出。

## 2026-05-31 — INDEX 是项目状态唯一真源，不能只看文档内状态字段

- **错误**：Review 测试报告时，只看了 `v0.4-test-report.md` 里的「Review 状态」表（写着 Developer 待 Review），就以为 Developer 还没 Review。实际上 INDEX 已反映 Developer ✅有条件通过 + 3 项收口事项待决。
- **根因**：启动后读了 INDEX，但后续工作时以单文档内的状态字段为准，没有以 INDEX 为最终真相。
- **纠错**：修正了 test-report.md / v0.4.md / INDEX 中我注入的过时信息；以 PM 视角对 3 项收口做了决定。
- **规则**：**项目级当前状态以 `docs/progress/INDEX.md` 为唯一真源**（runtime.md 已写明）。当文档内状态字段与 INDEX 矛盾时，以 INDEX 为准。启动后如果 INDEX 和文档状态不一致，应先修正文档再继续工作。
