## 阶段说明

本迭代包含三条主线：

1. **信息源管理重构**：将 Source 从空间附属配置提升为全局资产，建立空间 → 频道两级结构、展示位置、标签、运行状态、使用统计和告警入口。
2. **X/Twitter 实时监听**：一个 X Source 对应一个账号，所有启用账号共用一个 Filtered Stream 长连接，并保留 Source 级低频补偿抓取。
3. **信息评分方法论**：交付可 Review 的方法论草稿；本迭代不实现评分代码，不讨论日报、推送或评分后分流。

Owner 已确认当前旧业务数据没有保留价值。实施阶段清空旧业务数据，从空白状态启动新模型，不做旧业务数据迁移，不保留旧 API 兼容。

**架构发现（轻部署模式）**：`/var/www/news.huiyiyou.cloud` 是软链接到项目内 `frontend/dist/`，Developer `npm run build` 即生效，DevOps 不需要单独的 rsync 步骤。优点：单源真理零漂移。风险：无灰度、回滚需要重新 build 旧版本。本次 DevOps 一开始按 handbook 走了 rsync 步骤，被 `sent 716 bytes` 异常 + sha256 完全一致两条线索发现是软链接架构，已在 [`devops/full-stack-deploy-handbook.md`](../../knowledge/devops/full-stack-deploy-handbook.md) 增补「软链接部署模式」适配章节。

**部署期发现并已修复的两个隐藏问题**（详见 [DevOps 日志 2026-06-07 上线条目](../roles/devops.md)）：

1. **依赖未同步**：commit `75ca9ae` 引入 `undici@^7.27.2` 但部署机未跑 `npm install`，导致 worker 启动崩 `ERR_MODULE_NOT_FOUND`。部署中已修复（`npm install` 装 183 包）。
2. **drizzle journal 漂移**：DB schema 已被手动 patch 到 v0.5.1 状态，但 `__drizzle_migrations` 表只有 baseline，`_journal.json` 只有 0000/0001 两条而 disk 上有 0001-0004 四个 SQL。本次 restart 时 drizzle 幂等重跑 0001-0004（全部 IF [NOT] EXISTS 保护），journal 与 DB 状态自动对齐。属 [`db-migration-handbook`](../../knowledge/devops/db-migration-handbook.md) 既有故障排查类型，无新增风险。

## v0.5.1 — X 信息源反向同步（2026-06-07）

### 背景

v0.5 实现阶段 X Stream 是「平台推规则到 X」的方向：本地有 X Source → stream-manager 调 `POST /2/tweets/search/stream/rules` 同步到 Twitter。本地部署验证后 Owner 在 X Developer Portal 上手动维护了一条规则（`from:OpenAI` / tag `OpenAI官方账号`），本地 DB 还没有对应 Source。worker 启动时 `setRules([])` 把 Portal 上手动建的规则清空了——出现两个真理源冲突。

### 决策

Owner 当面拍板反转数据流：

1. X Developer Portal 上的 rules 成为唯一真理源，平台被动同步
2. X Source 平台不可新增/删除（只能去 Portal 操作），平台只能「暂停/恢复」
3. 暂停语义：tweet 继续入 `raw_items`，前端隐藏；恢复后历史立刻可见
4. 同步时机：worker 启动 + 每 5min 定时 + 管理页「同步 X 规则」按钮
5. X rule.tag → 本地 `display_name`（每次覆盖，UI 不可编辑）
6. 其它字段（domain_tags / source_role / attention_level / notes）平台维护、可编辑
7. 不再 polling，只走 Filtered Stream
