## 1. 迭代目标

v0.6 聚焦三件事：

1. 基于 `/root/news-aggregation-platform` Figma 导出原型重构现有 Vue 前端，并接入真实后端数据。
2. 围绕 X Source 建立 L0/L1 分层处理链路，把原始推文加工为可读、可理解、可展示的高价值新闻。
3. 支持空间图标上传，使空间入口具备更清晰的视觉识别能力。

一句话目标：

> 基于新 UI 原型重构信息消费界面，并围绕 X Source 建立 L0/L1 分层处理链路，让平台能够自动过滤明显无效推文，将有价值推文翻译、补全、分析、打标签并按时间流展示给用户。

## 2. 用户故事

### 2.1 高价值信息消费

作为 Owner，我想在新闻流中按时间顺序看到已经处理好的 X 高价值信息，以便快速浏览最新值得关注的内容。

验收要点：
- 新闻流展示 L1 处理完成的信息。
- 默认按原始发布时间倒序排列。
- 每条卡片展示标题、来源、发布时间、综合价值分、摘要和标签。
- 综合价值分用于辅助阅读优先级，不决定是否展示。

### 2.2 L1 四段式理解

作为 Owner，我想点击新闻卡片后在侧边抽屉中看到完整处理结果，以便理解原始推文到底在说什么、为什么重要。

验收要点：
- 点击新闻卡片打开右侧抽屉。
- 抽屉从右侧覆盖当前页面，新闻流主体不因抽屉打开而永久缩窄；桌面端建议宽度 420-520px，移动端全宽覆盖。
- 抽屉顶部固定展示标题、Source、原始发布时间、综合价值分、关闭按钮；内容区可滚动。
- 抽屉完整展示四段内容：
  1. 原文中文翻译
  2. 相关背景与补全
  3. AI 分析与评价
  4. AI 标签
- 抽屉布局顺序：
  1. 顶部摘要区：标题、Source、发布时间、综合价值分和 1-2 行摘要。
  2. 原文翻译区：展示原推文中文翻译，可折叠查看原文。
  3. 背景补全区：按段落展示背景信息，每段带来源标签和可信度标签。
  4. AI 分析区：展示为什么重要、可能影响和需要注意的不确定点。
  5. 评分区：展示四个维度分、理由和综合分计算结果。
  6. 标签区：按领域、实体、事件、内容类型、处理标签五组展示。
- 本期不做独立全屏详情页。
- 本期不做反馈按钮和反馈记录。

### 2.3 X 原始信息分层处理

作为 Owner，我想让所有抓取到的 X 原始信息先入库，再由系统进行 L0/L1 处理，以便既不丢原始数据，又能只展示处理完成的有价值内容。

验收要点：
- 所有抓取到的原始信息必须先入库。
- L0 只过滤明显无效内容，不做过度价值判断。
- L0 通过的信息进入 L1。
- L1 完成后进入新闻流展示。
- L0 skipped、L0/L1 failed、L1 processing 的信息不进入前台新闻流。
- 本期不做原始数据管理、归档、清理或保留周期配置；原始信息先入库是处理链路前提，不等于建设原始数据治理功能。

产品层状态机：

| 层级 | 状态 | 含义 | 前台新闻流可见性 | 管理/监控侧可见性 |
|------|------|------|------------------|-------------------|
| L0 | `pending` | 原始信息已入库，尚未开始 L0 判断 | 不可见 | 可见 |
| L0 | `processing` | L0 正在判断 | 不可见 | 可见 |
| L0 | `skipped` | L0 判定为明显无效或重复，不进入 L1 | 不可见 | 可见 |
| L0 | `passed` | L0 通过，已准备进入 L1 | 不可见，直到 L1 completed | 可见 |
| L0 | `failed` | L0 因系统错误失败 | 不可见 | 可见，可重试 |
| L1 | `not_started` | L0 尚未通过或 L1 尚未排队 | 不可见 | 可见 |
| L1 | `queued` | 已进入 L1 队列，等待处理 | 不可见 | 可见 |
| L1 | `processing` | L1 正在执行翻译、补全、分析、评分 | 不可见 | 可见 |
| L1 | `retryable_failed` | L1 因可重试错误失败，等待自动或手动重试 | 不可见 | 可见 |
| L1 | `final_failed` | L1 超过自动重试上限或遇到不可重试错误 | 不可见 | 可见 |
| L1 | `completed` | L1 处理完成，可进入新闻流 | 可见 | 可见 |

合法转移：

```text
raw item inserted
  -> L0 pending
  -> L0 processing
  -> L0 skipped
  -> L0 passed
       -> L1 queued
       -> L1 processing
       -> L1 completed
       -> L1 retryable_failed -> L1 queued -> L1 processing -> L1 completed
       -> L1 retryable_failed -> L1 final_failed
  -> L0 failed -> L0 pending / L0 processing
```

状态语义：
- `completed` 是唯一进入新闻流的 L1 状态。
- `skipped` 是正常终态，不算系统错误。
- `failed / retryable_failed / final_failed` 必须记录错误类型、失败原因、重试次数和最后失败时间。
- 重试成功后进入 `completed`，但排序仍使用原始发布时间；历史失败原因可保留在管理/监控侧，不影响新闻流展示。

### 2.4 L1 背景补全

作为 Owner，我想让系统对 X 推文进行必要的背景补全，以便短推文、暗语、项目代号或链接内容能被理解。

验收要点：
- 每条 L1 信息都进行库内相关新闻检索。
- 推文包含链接时，系统尝试读取链接内容。
- 当 `needs_context=true` 时，系统可以触发 X 搜索和 Web 搜索。
- 本期不读取评论作为 L1 必需补全来源。
- 背景补全必须展示来源标签。
- 链接读取、X 搜索和 Web 搜索失败时，L1 应降级继续执行；只有 LLM 主处理失败或输出结构不可用时才阻断 L1 completed。
- 外部依赖调用结果必须可观测：成功、失败、跳过原因和触发条件需要在管理/监控侧可查询。

### 2.5 L1 价值评分

作为 Owner，我想看到每条 L1 信息的综合价值分和评分依据，以便判断阅读优先级。

验收要点：
- AI 输出四个维度分和理由：
  - 时效性
  - 影响力
  - 置信度
  - 可理解度
- 系统按权重计算综合价值分，不由 AI 直接拍脑袋输出。
- 初版权重：
  - 时效性：25%
  - 影响力：35%
  - 置信度：25%
  - 可理解度：15%
- 卡片展示 `1-10` 综合价值分。
- 抽屉中展示维度分和理由。

## 3. 验收标准

### 3.1 L0 入库和状态

AC-01：当系统抓取到任意 X 原始信息时，应该先保存原始记录，不因 L0 判断而物理丢弃。

AC-02：当原始信息进入 L0 时，系统应该记录 L0 处理状态、L0 标签、处理时间和失败原因（如有）。

AC-03：当 L0 判断信息为空文本、乱码、纯 emoji、纯转发无新增文本、明显重复、抽奖/招聘/无关广告、与 Source 主题明显无关或已处理过同 URL / 同 tweet id 时，应该标记为 skipped，不进入 L1。

AC-04：当 L0 通过时，系统应该将信息送入 L1，并保留 L0 标签，例如 normal_candidate、high_priority_candidate、needs_context_candidate。

AC-04a：L0 和 L1 状态应该使用 §2.3 定义的状态枚举；任何新状态必须先更新 PRD 或设计文档并说明兼容关系。

### 3.2 L1 处理和重试

AC-05：当信息进入 L1 时，系统应该生成中文标题、摘要、原文中文翻译、背景补全、AI 分析评价、AI 标签、四维评分和综合价值分。

AC-06：当 L1 处理完成时，系统应该将该信息展示在新闻流中，并按原始发布时间倒序排序。

AC-07：当 L1 处理中发生临时错误（LLM 超时、模型服务异常、JSON 格式错误、搜索服务异常、链接读取超时、速率限制、临时网络错误）时，系统应该记录失败原因、重试次数和下次重试时间。

AC-08：当 L0/L1 处理失败且属于可重试错误时，系统应该自动重试最多 3 次，退避间隔为 1 分钟、5 分钟、15 分钟；该退避策略只适用于 L0/L1 处理任务，不应改变既有 `fetch_source`、`process_raw_item` 等任务类型的退避行为。

AC-09：当自动重试超过最大次数后，系统应该标记为最终失败，不进入新闻流。

AC-10：当 L1 失败信息后续重试成功时，系统应该进入新闻流，但排序仍按原始发布时间计算。

AC-10a：当单条 L1 因外部依赖失败进入 `retryable_failed` 或 `final_failed` 时，同 Source 的其他原始信息应该继续正常执行 L0/L1，不应被单条失败阻塞。

错误分类：

| 类型 | 示例 | 行为 |
|------|------|------|
| 可重试 | LLM 超时、LLM 5xx、网络超时、临时 DNS/代理错误、搜索服务 429、搜索服务 5xx、链接读取超时 | 进入 `retryable_failed`，按 AC-08 重试 |
| 可降级 | 链接读取失败、X 搜索失败、Web 搜索失败、外部搜索未配置 | 记录失败或跳过原因，继续 L1 主处理 |
| 不可重试 | 原始内容结构缺失、Source 已删除、认证配置缺失或 401/403、AI 输出连续结构不合法且达到重试上限 | 进入 `final_failed` |

### 3.3 L1 补全来源

AC-11：每条 L1 信息都应该执行库内相关新闻检索，并将相关结果作为背景补全输入。

AC-12：当推文包含链接时，系统应该尝试读取链接内容；读取失败时记录失败原因，但不阻塞 L1。

AC-13：当 L1 判断 `needs_context=true` 时，系统应该可以触发 X 搜索和 Web 搜索；不是每条 L1 信息都必须外部搜索。

AC-14：当背景补全使用 Source 信息、链接内容、库内相关新闻、X 搜索或 Web 搜索时，抽屉应该展示对应来源标签。

AC-15：当补全内容包含推断或不确定信息时，系统应该在背景补全中区分已确认事实、合理推断和不确定点。

AC-15a：背景补全段落应同时支持两类标记：来源标签（Source / 链接 / 库内相关新闻 / X 搜索 / Web 搜索）和可信度标签（已确认事实 / 合理推断 / 不确定点）。

### 3.4 评分和标签

AC-16：当 L1 生成评分时，AI 应输出时效性、影响力、置信度、可理解度四个 `1-5` 维度分和理由。

AC-17：系统应该按 25% / 35% / 25% / 15% 权重计算 `1-10` 综合价值分。

AC-18：新闻卡片应该展示综合价值分，抽屉应该展示维度分和理由。

AC-19：AI 标签应该按分类输出，不混成一个大数组：
  - 领域标签
  - 实体标签
  - 事件标签
  - 内容类型
  - 处理标签

评分和标签展示规则：
- 综合价值分保留 1 位小数，卡片展示综合分，抽屉展示综合分和四维明细。
- 每个维度理由建议 1 句话，不超过 80 个中文字符。
- 五类标签允许 AI 自由生成；前端需要支持未知标签默认样式，不要求本期建设标签管理后台。
- 卡片只展示最关键的 2-4 个标签；抽屉展示五类完整标签。

### 3.5 前端展示

AC-20：新闻流应该展示 L1 completed 信息，不展示 L0 skipped、L1 processing、L1 failed 信息。

AC-21：新闻卡片应该包含标题、来源、发布时间、综合价值分、摘要和标签。

AC-22：点击新闻卡片时，应该打开右侧抽屉，抽屉展示四段式 L1 内容。

AC-23：本期不应出现独立全屏新闻详情页入口；Source 详情页不属于新闻详情页，不受此限制。

AC-24：v0.6 用户可见路径不引入反馈按钮、反馈记录或评论式交互。

AC-25a：生产构建页面渲染数据必须来自真实 API；mock fixture 不得被 prod build 引用。

AC-25b：开发期允许使用 mock fixture 跑视觉和组件状态；fixture 必须与后端契约字段对齐，并在切换真实 API 时删除正式路径引用。

AC-25c：接口字段缺失时，前端应优先隐藏对应非关键元素或展示空状态，不得回退到 mock 数据伪装真实内容。

### 3.6 空间图标上传

AC-26：空间编辑入口应该支持上传图片图标，同时保留 emoji 或文本图标能力。

AC-27：当上传的文件类型或大小不符合限制时，系统应该给出明确错误提示。

AC-28：当空间图标上传、替换或移除成功后，新闻浏览页空间入口和管理页应该展示最新图标。

AC-28a：当上传过程发生存储失败、网络中断或并发覆盖冲突时，系统应该保留上传前图标并给出错误提示。

AC-28b：替换或移除图片图标后，旧文件应由后端清理或标记为可清理，避免长期占用磁盘。

### 3.7 监控、路由和手动重试

AC-29：告警和日志应合并到统一监控页，页面内至少区分告警视图和日志视图；旧告警/日志入口应跳转到新监控页的对应视图。

AC-30：统一监控页或 Source 详情页应展示 L0/L1 最近处理状态计数，包括 completed、skipped、retryable_failed、final_failed。

AC-31：L1 手动重试入口只在管理/监控侧出现，不在新闻消费侧出现。

AC-32：当外部依赖连续失败、L0/L1 队列长时间无进展或 L1 final_failed 数量异常增长时，系统应产生可见告警或监控记录。

### 3.8 不回归验收

AC-33：本期改动不得破坏 v0.5 已上线的信息源管理、空间/频道管理、X Stream 连接、timeline 补偿抓取和新闻流基础展示。

AC-34：L0/L1 专用重试策略不得改变既有抓取任务的重试行为。

AC-35：部署前应检查生产构建未引用 mock fixture，且统一监控页、新闻页、管理页、Source 详情页均能从真实 API 渲染。

### 4.3 Source 信息使用边界

L1 处理时，Source 的账号身份、领域标签、备注和关注方向可以作为 AI 理解原始推文的上下文输入，用于辅助判断内容含义、相关性和价值。

Source 信息不得机械决定评分结果：
- 核心账号不等于自动高分。
- 官方账号不等于自动置信度 5。
- 非核心账号不等于自动低分。

最终评分必须基于推文本身、补全结果、来源证据和 AI 理由共同生成。

## 6. 风险和开放问题

### 6.1 风险

- L1 链路依赖 LLM、搜索和链接读取，失败面比 v0.5 更大。
- 外部搜索和链接读取可能带来成本、延迟、速率限制和不稳定性。
- AI JSON 输出可能不稳定，需要强校验和重试。
- 库内相关新闻检索如果设计过重，可能拖慢 L1 处理。
- Figma 原型是 React 项目，迁移到 Vue 时需要避免机械照搬组件结构。
- 空间图标上传涉及文件存储、访问路径、缓存和部署回滚；不得存入前端构建目录。
- 本期不做原始数据归档/清理，随着 X Source 数量增长，后续可能出现 raw_items 和任务日志增长风险；当前 Owner 判断信息源较少，本期先不建设治理能力。
- 本期不设置成本上限或预算熔断，短期基于少量信息源接受成本波动；后续信息源规模扩大后需要重新评估。
- 告警/日志路由合并会改变现有入口，需要兼容旧路径，避免已有书签或内部链接失效。

### 6.2 开放问题

- Web 搜索与 X 搜索具体使用哪个服务或接口，由 Architect / Developer / DevOps 在设计阶段确认；产品边界已定为可选增强、失败不阻断 L1。
- 库内相关新闻检索的匹配算法、召回数量和排序规则由 Architect 在设计阶段确认。
- 图片上传具体持久目录、URL 规则、nginx/Fastify 静态服务方式由 Architect / DevOps 在设计阶段确认；不得使用前端构建目录。
- 统一监控页的具体信息架构和筛选项由 UI 在 UI 方案阶段细化；PRD 已确定告警/日志本期合并。

#### 中严重度（4 条）

**#A12（中）§3.2 错误分类表中"链接读取超时"归"可重试"档，与 AC-12「读取失败不阻塞 L1」直接矛盾**

- 关联：§3.2 错误分类表、AC-12
- 现状：§3.2 表中
  - 可重试档列出：「LLM 超时、LLM 5xx、网络超时、临时 DNS/代理错误、搜索服务 429、搜索服务 5xx、**链接读取超时**」

- 问题：链接读取超时和链接读取失败本质上都是"链接读取这个外部依赖出错了"。如果按"可重试"处理，整个 L1 会重试 3 次（按 AC-08），每次都因这条链接超时挂掉 → L1 进入 `final_failed`。但 AC-12 明确写"读取失败时记录失败原因，但**不阻塞** L1"，意味着链接读取任何失败（含超时）都应当降级让 L1 主处理继续。两者执行路径相反。

- 修改建议：「链接读取超时」从可重试档移到可降级档。可降级档调整为：「链接读取失败 / 链接读取超时、X 搜索失败 / 超时、Web 搜索失败 / 超时、外部搜索未配置」。
- 优先级：R3 可顺手改；如不改也可设计文档定义"链接读取被 L1 主处理调用时单独走可降级路径"作为兜底，但 PRD 自洽性差。

**#A13（中）§2.3 状态机：L0 没有 `retryable_failed` 状态导致 L0 失败重试机制与 L1 不对称，AC-08「3 次重试退避对 L0/L1」在 L0 实现上路径不明**

- 关联：§2.3 状态机表、§2.3 转移图、AC-08
- 现状：§2.3 状态枚举表中
  - L0 状态：`pending / processing / skipped / passed / failed`（5 态，**无 retryable_failed**）
  - L1 状态：`not_started / queued / processing / retryable_failed / final_failed / completed`（6 态，**有 retryable_failed**）
- 转移图写「L0 failed -> L0 pending / L0 processing」—— L0 失败后可以回 pending 重试。
- 问题：AC-08「L0/L1 处理失败且属于可重试错误时，自动重试最多 3 次」适用 L0 和 L1 两层，但状态机层面：
  - L1 走 `processing → retryable_failed → queued → processing → completed/final_failed` 清晰可见
  - L0 走 `processing → failed → pending → processing → ?` 模糊。L0 failed 是终态还是中间态？如果是中间态（可回 pending），那 L0 final_failed 在哪里？转移图没画 L0 的"终态失败"路径。
- 设计阶段实现路径：要么 L0 也加 `retryable_failed` + `final_failed`（与 L1 对称，推荐），要么 L0 只有 failed 终态、attempt 计数直接累积在 failed 内（不对称但更省状态枚举）。两者数据模型不同。
- 修改建议：二选一并写明
  - 方案 A（推荐，与 L1 对称）：L0 加 `retryable_failed` + `final_failed`，与 L1 状态命名对齐，转移图改为 `L0 processing → L0 retryable_failed → L0 pending → ... → L0 final_failed`
  - 方案 B（保留当前）：明确 L0 只有 failed 单一失败态，AC-08 在 L0 层通过 attempt 累积实现，达到上限后 failed 变为最终终态。需要在 §2.3 状态语义段补"L0 failed 在重试次数达上限后即为终态"。
- 优先级：R3 修订。两个方案都不影响整体架构，但 PRD 不能两个都不选。

**#A14（中）§3.7 AC-30 "统一监控页 **或** Source 详情页展示 L0/L1 状态计数"的"或"字让 UI/Developer 二选一，应改为双表达**

#### 高严重度

**#O1（高）四类外部依赖的网络出口、超时、成本、速率限制在 PRD 完全缺失，部署侧无法做 dry-check 与熔断设计**

- 关联：AC-07、AC-08、AC-11、AC-12、AC-13、§5 前置依赖、§6.1
- 同源：Architect #A3（候选选型）
- DevOps 视角独立部分：

**#O3（高）软链接部署模式 × 空间图标上传：存储路径选错会让用户上传文件在每次 build 时丢失，PRD 没把"不得放 frontend/dist 内"列为硬约束**

**#O4（高）L0/L1 卡住、外部依赖宕机、月费突破等运维事件的告警载体未在 PRD 收敛，DevOps 无法在设计阶段挂告警**

  - 这些指标对应的可观测字段建议在 DB schema 体现（与 #T7 可观测载体方向一致，但落到具体告警判定逻辑）。

  - AC-15 的"事实/推断/不确定"标签是用哪种载体表达（图标 / 文字前缀 / 段落标签），与 AC-14 来源标签共存的呈现方式。

**#A7（中）"库内相关新闻检索"算法策略未定义**

- 关联：AC-11、§6.2 开放问题第 2 条
- 问题：AC-11 强制"每条 L1 都执行库内检索"，但检索方式（关键词 ILIKE / pgvector 向量 / Elasticsearch 全文 / OpenAI embedding）会带来**架构层差异巨大**的方案：
  - 向量检索需要新增表存 embedding + 选 embedding 模型 + 决定何时更新。
  - 全文检索需要新建 `tsvector` 列 + GIN 索引或引入新服务。
  - ILIKE 简单但召回质量低，且 PG 性能不行。
- 这同样不是"设计阶段实现细节"，而是会决定**是否新增基础设施**和**是否额外烧 LLM token 做 embedding**。
- 修改建议：PRD 在 §5 前置依赖给出候选清单 + 倾向方案；如真要留到设计阶段，至少把"是否引入新基础设施（embedding 服务 / 全文索引）"的决策标准写明（如：日处理量 X 条以下用 ILIKE，以上才上向量）。

**#A8（中）空间图标上传的存储位置、文件名规范、清理策略未在 PRD 收敛**

- 关联：AC-26、AC-27、AC-28、§6.2 开放问题第 3 条
- 问题：§6.2 把"图片上传存储位置（本地静态目录、数据库引用、对象存储或其他）"标为"由 Architect / DevOps 在设计阶段确认"。但这同样是产品/部署决策不是架构选型：
  - 本地静态目录 → 部署回滚时文件可能丢失（v0.5 已踩过部署架构坑，参考 [`full-stack-deploy-handbook.md`](../knowledge/devops/full-stack-deploy-handbook.md) 软链接模式）。
  - 数据库 bytea → 拖慢 SELECT。
  - 对象存储 → 新增成本/账号/部署密钥。
- AC-27 要求"文件类型和大小限制"，但 PRD 没给具体阈值（MIME 白名单 / 最大 KB / 分辨率上限）。
- AC-28 说"上传/替换/移除后展示最新图标"，没说替换/移除是否要清理旧文件（避免长期占用磁盘）。
- 修改建议：PRD §3.6 补充：
  - 限制：MIME 白名单（如 `image/png, image/jpeg, image/webp`）+ 最大文件大小（建议 ≤ 500KB）+ 最大分辨率（建议 256×256，因为图标场景）。
  - 存储位置候选 + 倾向方案 + 兜底；明确替换/移除是否要清理旧文件。

#### 中严重度

**#D5（中）AC-05 要求 L1 输出"中文标题、摘要、原文翻译、背景补全、AI 分析评价、AI 标签、四维评分"，但 AI 单次调用是否能稳定输出这么大的 JSON 没评估**

- 关联：AC-05、AC-16、AC-19
- 问题：现有 `processLLM` 输出的 JSON 大约 5 个 top-level key，体量在 1-2KB；本期要求的 JSON 至少 11 个 top-level key（title/summary/translation/context/analysis/tags×5 类/dimensions/scores/source_refs），加上"补全来源标签"（#A6）和"事实/推断/不确定"分类（#A6），单次输出可能在 5-10KB。问题：
  - LLM 输出越长，JSON 解析失败率越高（v0.5 已经踩过 `extractFirstJsonObject` 不稳定的坑）。
  - 单次调用如果失败要全部重做，token 浪费大。
  - 是否拆为多次调用（L1a 翻译+摘要 / L1b 评分+标签 / L1c 背景补全）？这样可以局部重试，但 token 成本和延迟上升。
- 风险：开发实施时如果走单次调用 → L1 成功率可能只有 70-80%（v0.5 评估值），AC-08 的 3 次重试会被频繁触发，LLM 成本失控。
- 修改建议：PRD §3.2 或 §6.1 风险段加一段"LLM 调用策略"：
  - 单次 vs 多次调用方案的取舍由设计阶段决定，但 PRD 应给"上限约束"：例如单次调用输出不超过 4KB / token 不超过 N。
  - 如果走多次调用，PRD 应明确**部分成功是否进入新闻流**（如翻译+评分成功但背景补全失败 → 是 L1 completed 还是 L1 partial？）——这是产品决策。

**#D6（中）AC-19 五类标签如果 AI 自由生成（#A5），前端如何稳定渲染"未知标签 → 默认样式"PRD 没规则**

- 关联：AC-19、AC-21、AC-22
- 问题：与 Architect #A5 / UI #U4 同向，Developer 视角是：
  - 如果 5 类标签是闭集枚举（如领域 = AI/财经/科技/其他），前端可以用 TS 枚举 + 颜色字典渲染；
  - 如果 AI 自由生成，前端要做的是"按字符串 hash 分配颜色"（v0.5 的 `TagChip` 已经是这套），但 5 类同时存在时颜色冲突如何避免？
  - 数据形态：`tags: { domain: string[], entity: string[], event: string[], content_type: string[], processing: string[] }` —— PRD 没确认这是不是最终结构。如果设计阶段才定，前端无法预先建组件 props。
- 风险：前端组件无法在前期建好，等到设计阶段再返工，重构成本高。
- 修改建议：PRD §3.4 给出**标签数据结构草案**（即使开闭集还没定）：例如 `tags = { domain: TagItem[], entity: TagItem[], event: TagItem[], content_type: TagItem[], processing: TagItem[] }`，每个 `TagItem = { name: string, value?: string, confidence?: number }`。允许 AI 自由生成的字段也要先把"结构骨架"定下来。

**#D7（中）前端重构覆盖 10 个页面（§2.6），但实际工程量没估，"现有 Vue 组件迁移"边界不清**

- 关联：§2.6
- 问题：v0.5 留下了 21 个 Vue 组件（已 grep 确认 `frontend/src/components/` 下 22 个文件），原型有 30+ React 组件。PRD §2.6 列了 10 个页面，但：
  - 哪些 v0.5 组件可以直接复用（如 `StatusBadge`、`Pagination`、`SourceTable`）？
  - 哪些必须重写（如新闻卡片要展示 5 类标签 + 4 维分 + 综合分，原 `NewsListItem` 不够）？
  - 哪些可以删除（如原型不再需要的组件）？
- v0.5 经验值：实现阶段先做组件清单（保留/重写/删除）才能精准估工时，本期 PRD 不给的话设计阶段架构师又要做清单。
- 修改建议：PRD §2.6 加一句"现有 Vue 组件迁移策略由设计阶段产出清单"，**并把'重构最大工作量页面'按 P0/P1/P2 标出**——例如 P0 = NewsPage（含卡片 + 抽屉 + 筛选）、P1 = AdminPage、P2 = SourceDetailPage。这样实施时可按优先级分批合并。

**#D8（中）AC-15「区分已确认事实、合理推断、不确定点」前端如何承载，Developer 实现成本估算缺信息**

- 关联：AC-15、AC-14
- 问题：与 UI #U5 同向，Developer 看视觉层级 + 数据载体的协同：
  - 如果 AI 输出 `context: string`（一段纯文本，不带分类）→ 前端无法做置信度区分；
  - 如果 AI 输出 `context: Array<{ text, confidence, source }>`（分句结构）→ 前端可以做但 LLM 输出复杂度极高（参考 #D5 风险）；
  - 折中：AI 输出 `context: { confirmed: string, inferred: string, uncertain: string }`（按段落分类）→ 实现成本中等。
- 风险：开发选择不同载体，前端组件结构差异巨大，实施时无法快速重写。
- 修改建议：PRD §3.3 在 #A6/#U5 的"段落级"决定基础上，明确数据载体：例如 `context = { sections: [{ kind: 'confirmed'|'inferred'|'uncertain', source: 'source_info'|'link_content'|'kb_search'|'x_search'|'web_search', text: string }] }`。粒度可大可小，但**结构必须 PRD 定**，否则前端组件 props 无法稳定。

**#D9（中）AC-11「每条 L1 都执行库内检索」对 LLM 链路延迟和成本的影响未量化，开发无法判断是否同步阻塞**

- 关联：AC-11、§6.1
- 问题：与 Architect #A7 同向，Developer 关心**调用是同步还是异步**：
  - 同步检索（每条 L1 先 SQL 检索 → 拼上下文 → 调 LLM）→ 阻塞 L1 处理，但实现简单；
  - 异步检索（先发 L1 LLM 调用，检索结果作为补充材料二次调用）→ 复杂但延迟低。
  - 检索结果送入 LLM 上下文的体量上限是多少（5 条 / 10 条 / 20 条）？token 成本如何控制？
- 风险：开发拍脑袋实现，可能让 L1 平均处理时间从 5s 飙到 30s，影响实时性。
- 修改建议：PRD §3.3 加一句"库内检索策略"：候选条数上限 + 同步 vs 异步 + 召回失败是否阻塞 L1（推荐：异步、上限 5 条、召回失败不阻塞）。

**#D10（中）"前端真实数据联调" 的环境依赖未列：本地开发是否要后端先实现 L0/L1？没有 mock 路径如何前后端并行？**

- 关联：AC-25、§5、§6.2
- 问题：与 #D1 互补，开发实操层面：
  - 前端开发员本地起 `npm run dev` 时，后端是否已经完整运行（含 L0/L1 worker）？v0.5 经验是经常本地后端 + 远程 DB；本期 L0/L1 还要依赖 LLM/搜索 API，本地是否需要这些 key？
  - Tester 联调本地是否能用？联调测试库是否要有"已 L1 completed 的样例数据"？
  - CI 自动化测试如何 mock LLM（v0.5 测试已经禁用，恢复测试时本期依赖如何打桩）？
- 风险：实施时本地开发环境差异大，前端工程师可能没法稳定跑前端联调。
- 修改建议：PRD §5 前置依赖 加一段"开发联调环境"：本地是否需要全套 LLM/搜索 key、是否提供 mock LLM 模式、Tester 联调样例数据如何造（推荐沿用 v0.5 "后台 DB 直造" 路径）。
