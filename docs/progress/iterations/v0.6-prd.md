## 1. 迭代目标

v0.6 聚焦三件事：

1. 基于 `/root/news-aggregation-platform` Figma 导出原型重构现有 Vue 前端，并接入真实后端数据。
2. 围绕 X Source 建立 L0/L1 分层处理链路，把原始推文加工为可读、可理解、可展示的高价值新闻。
3. 支持空间图标上传，使空间入口具备更清晰的视觉识别能力。

一句话目标：

> 基于新 UI 原型重构信息消费界面，并围绕 X Source 建立 L0/L1 分层处理链路，让平台能够自动过滤明显无效推文，将有价值推文翻译、补全、分析、打标签并按时间流展示给用户。

## 2. 用户故事

### 2.1 高价值信息消费

作为 Owner，我想在新闻流中按时间顺序看到已经处理好的 X 高价值信息，以便快速浏览最新值得关注的内容。

验收要点：
- 新闻流展示 L1 处理完成的信息。
- 默认按原始发布时间倒序排列。
- 每条卡片展示标题、来源、发布时间、综合价值分、摘要和标签。
- 综合价值分用于辅助阅读优先级，不决定是否展示。

### 2.2 L1 四段式理解

作为 Owner，我想点击新闻卡片后在侧边抽屉中看到完整处理结果，以便理解原始推文到底在说什么、为什么重要。

验收要点：
- 点击新闻卡片打开右侧抽屉。
- 抽屉完整展示四段内容：
  1. 原文中文翻译
  2. 相关背景与补全
  3. AI 分析与评价
  4. AI 标签
- 本期不做独立全屏详情页。
- 本期不做反馈按钮和反馈记录。

### 2.3 X 原始信息分层处理

作为 Owner，我想让所有抓取到的 X 原始信息先入库，再由系统进行 L0/L1 处理，以便既不丢原始数据，又能只展示处理完成的有价值内容。

验收要点：
- 所有抓取到的原始信息必须先入库。
- L0 只过滤明显无效内容，不做过度价值判断。
- L0 通过的信息进入 L1。
- L1 完成后进入新闻流展示。
- L0 skipped、L0/L1 failed、L1 processing 的信息不进入前台新闻流。

### 2.4 L1 背景补全

作为 Owner，我想让系统对 X 推文进行必要的背景补全，以便短推文、暗语、项目代号或链接内容能被理解。

验收要点：
- 每条 L1 信息都进行库内相关新闻检索。
- 推文包含链接时，系统尝试读取链接内容。
- 当 `needs_context=true` 时，系统可以触发 X 搜索和 Web 搜索。
- 本期不读取评论作为 L1 必需补全来源。
- 背景补全必须展示来源标签。

### 2.5 L1 价值评分

作为 Owner，我想看到每条 L1 信息的综合价值分和评分依据，以便判断阅读优先级。

验收要点：
- AI 输出四个维度分和理由：
  - 时效性
  - 影响力
  - 置信度
  - 可理解度
- 系统按权重计算综合价值分，不由 AI 直接拍脑袋输出。
- 初版权重：
  - 时效性：25%
  - 影响力：35%
  - 置信度：25%
  - 可理解度：15%
- 卡片展示 `1-10` 综合价值分。
- 抽屉中展示维度分和理由。

### 2.6 Figma 原型前端重构

作为 Owner，我想让当前 Vue 前端按 `/root/news-aggregation-platform` 原型重构，以便页面结构、信息密度和交互符合新的使用方式。

验收要点：
- 不直接迁入 React 原型。
- 在现有 Vue3 + TS + Vite 前端中实现。
- 页面结构和视觉参考 `/root/news-aggregation-platform`。
- 需要接真实后端 API，不保留 mock 数据作为正式路径。
- 覆盖页面：
  - 全局导航和布局
  - 新闻浏览页
  - 管理页
  - Source 详情页
  - 告警/日志监控页
  - 添加信息源抽屉
  - 编辑/删除弹窗
  - 统计卡片
  - 空间/频道筛选
  - 信息源库表格

### 2.7 空间图标上传

作为 Owner，我想为空间设置图片图标，以便不同空间在新闻浏览和管理界面中更容易识别。

验收要点：
- 空间支持上传图片图标。
- 保留现有 emoji 或文本图标能力。
- 支持替换、移除图片图标。
- 限制文件类型和大小。
- 上传失败时给出明确错误提示。
- 空间入口和管理页展示上传后的图标。

## 3. 验收标准

### 3.1 L0 入库和状态

AC-01：当系统抓取到任意 X 原始信息时，应该先保存原始记录，不因 L0 判断而物理丢弃。

AC-02：当原始信息进入 L0 时，系统应该记录 L0 处理状态、L0 标签、处理时间和失败原因（如有）。

AC-03：当 L0 判断信息为空文本、乱码、纯 emoji、纯转发无新增文本、明显重复、抽奖/招聘/无关广告、与 Source 主题明显无关或已处理过同 URL / 同 tweet id 时，应该标记为 skipped，不进入 L1。

AC-04：当 L0 通过时，系统应该将信息送入 L1，并保留 L0 标签，例如 normal_candidate、high_priority_candidate、needs_context_candidate。

### 3.2 L1 处理和重试

AC-05：当信息进入 L1 时，系统应该生成中文标题、摘要、原文中文翻译、背景补全、AI 分析评价、AI 标签、四维评分和综合价值分。

AC-06：当 L1 处理完成时，系统应该将该信息展示在新闻流中，并按原始发布时间倒序排序。

AC-07：当 L1 处理中发生临时错误（LLM 超时、模型服务异常、JSON 格式错误、搜索服务异常、链接读取超时、速率限制、临时网络错误）时，系统应该记录失败原因、重试次数和下次重试时间。

AC-08：当 L0/L1 处理失败且属于可重试错误时，系统应该自动重试最多 3 次，退避间隔为 1 分钟、5 分钟、15 分钟。

AC-09：当自动重试超过最大次数后，系统应该标记为最终失败，不进入新闻流。

AC-10：当 L1 失败信息后续重试成功时，系统应该进入新闻流，但排序仍按原始发布时间计算。

### 3.3 L1 补全来源

AC-11：每条 L1 信息都应该执行库内相关新闻检索，并将相关结果作为背景补全输入。

AC-12：当推文包含链接时，系统应该尝试读取链接内容；读取失败时记录失败原因，但不阻塞 L1。

AC-13：当 L1 判断 `needs_context=true` 时，系统应该可以触发 X 搜索和 Web 搜索；不是每条 L1 信息都必须外部搜索。

AC-14：当背景补全使用 Source 信息、链接内容、库内相关新闻、X 搜索或 Web 搜索时，抽屉应该展示对应来源标签。

AC-15：当补全内容包含推断或不确定信息时，系统应该在背景补全中区分已确认事实、合理推断和不确定点。

### 3.4 评分和标签

AC-16：当 L1 生成评分时，AI 应输出时效性、影响力、置信度、可理解度四个 `1-5` 维度分和理由。

AC-17：系统应该按 25% / 35% / 25% / 15% 权重计算 `1-10` 综合价值分。

AC-18：新闻卡片应该展示综合价值分，抽屉应该展示维度分和理由。

AC-19：AI 标签应该按分类输出，不混成一个大数组：
  - 领域标签
  - 实体标签
  - 事件标签
  - 内容类型
  - 处理标签

### 3.5 前端展示

AC-20：新闻流应该展示 L1 completed 信息，不展示 L0 skipped、L1 processing、L1 failed 信息。

AC-21：新闻卡片应该包含标题、来源、发布时间、综合价值分、摘要和标签。

AC-22：点击新闻卡片时，应该打开右侧抽屉，抽屉展示四段式 L1 内容。

AC-23：本期不应出现独立全屏详情页入口。

AC-24：本期不应出现反馈按钮、反馈记录或评论式交互。

AC-25：前端重构页面必须接真实后端 API，不得用 mock 数据作为正式展示路径。

### 3.6 空间图标上传

AC-26：空间编辑入口应该支持上传图片图标，同时保留 emoji 或文本图标能力。

AC-27：当上传的文件类型或大小不符合限制时，系统应该给出明确错误提示。

AC-28：当空间图标上传、替换或移除成功后，新闻浏览页空间入口和管理页应该展示最新图标。

## 4. 范围边界

### 4.1 本迭代做

- 基于 `/root/news-aggregation-platform` 原型重构现有 Vue 前端对应页面。
- 接入真实后端 API，清理正式路径中的 mock 数据。
- X 信息 L0/L1 分层处理。
- 所有原始信息入库。
- L0 状态、L0 标签、L1 状态、L1 标签、失败原因、重试次数、下次重试时间。
- L1 四段式内容生成和抽屉展示。
- 库内相关新闻检索。
- 链接读取。
- 按 `needs_context` 触发 X 搜索和 Web 搜索。
- 四维评分和综合价值分计算。
- 五类 AI 标签。
- 空间图标上传、替换、移除。

### 4.2 本迭代不做

- 不做 L2 事件追踪。
- 不做时间线分析。
- 不做深度搜索和深度分析工作流。
- 不做公众号文章或系列文章生成。
- 不做反馈按钮、反馈记录或评论能力。
- 不做独立全屏新闻详情页。
- 不读取评论作为 L1 必需补全来源。
- 不把 React 原型直接迁入生产代码。
- 不做前端可配置的信息处理工作流。
- 不在前端展示分流策略。
- 不提供处理工作流配置接口。
- 不做前端 Source 级代理配置。
- 不做自定义代理池、自动代理切换或代理健康检查平台。
- 不做完整领域标签管理后台；L1 AI 标签按本迭代输出结构生成和展示。
- 不对所有历史新闻强制重算。

### 4.3 Source 信息使用边界

L1 处理时，Source 的账号身份、领域标签、备注和关注方向可以作为 AI 理解原始推文的上下文输入，用于辅助判断内容含义、相关性和价值。

Source 信息不得机械决定评分结果：
- 核心账号不等于自动高分。
- 官方账号不等于自动置信度 5。
- 非核心账号不等于自动低分。

最终评分必须基于推文本身、补全结果、来源证据和 AI 理由共同生成。

## 5. 前置依赖

- `/root/news-aggregation-platform` 原型项目可作为 UI 输入材料读取。
- 现有 Vue 前端继续作为生产前端基础。

- 需要 DevOps 确认外部搜索、链接读取、图片上传存储和 LLM 调用在部署环境中的网络与成本约束。

## 6. 风险和开放问题

### 6.1 风险

- L1 链路依赖 LLM、搜索和链接读取，失败面比 v0.5 更大。
- 外部搜索和链接读取可能带来成本、延迟、速率限制和不稳定性。
- AI JSON 输出可能不稳定，需要强校验和重试。
- 库内相关新闻检索如果设计过重，可能拖慢 L1 处理。
- Figma 原型是 React 项目，迁移到 Vue 时需要避免机械照搬组件结构。
- 空间图标上传涉及文件存储、访问路径、缓存和部署回滚，需要设计清楚。

### 6.2 开放问题

- Web 搜索与 X 搜索具体使用哪个服务或接口，由 Architect / Developer / DevOps 在设计阶段确认。
- 库内相关新闻检索的匹配算法、召回数量和排序规则由 Architect 在设计阶段确认。
- 图片上传存储位置（本地静态目录、数据库引用、对象存储或其他方案）由 Architect / DevOps 在设计阶段确认。
- L1 处理失败后的手动重试入口本期是否需要页面化，由设计阶段结合实现成本确认；PRD 只要求后端具备状态和自动重试能力。

### Architect R1（2026-06-09）

**结论**：❌ 需修改。共 11 条意见（3 高 / 5 中 / 3 低）。

整体评价：v0.6 三条主线方向正确。前端重构沿用现有 Vue3 栈不直接迁 React 原型的判断稳妥（§4.2/§2.6/§6.1）；L0/L1 分层和"原始信息先入库"的原则与现有 `raw_items / processed_news / tasks` 架构方向一致，可在 v0.5 基线上做加法实现。但本轮 PRD 在**状态机定义、外部依赖收敛、评分数据形态、补全来源标签结构、空间图标上传策略**这五块仍有结构性缺口，进入设计阶段前必须修正，否则 Architect 阶段会被迫越界做产品决策。

#### 高严重度

**#A1（高）L0/L1 状态机未在 PRD 定稿，AC-07/AC-08/AC-09 不可测、不可设计**

- 关联：AC-03、AC-04、AC-07、AC-08、AC-09、AC-10、AC-20、§3.2 整段
- 问题：PRD 中散落出现多种状态词："L0 skipped/L0 通过"、"L0/L1 failed"、"L1 processing/completed"、"最终失败"、"L1 失败信息后续重试成功"。但缺少一张明确的状态枚举表 + 合法转移图：
  - L0 是否有 `pending` / `running` / `skipped` / `passed` / `failed` 五态，还是只有终态？
  - L1 是否有 `pending` / `running` / `completed` / `failed` / `permanently_failed`？
  - "最终失败"（AC-09）与"L1 failed"（AC-07）是不同状态还是同一终态？
  - AC-10「失败后重试成功进入新闻流」意味着允许从 `failed` → `completed` 的回流转移，需明确这个回流路径以及是否清空之前的 `last_error`。
  - L0/L1 是落在同一个状态字段还是两个状态字段？建议两个（分层独立），但 PRD 没说。
- 风险：架构师无法画状态机，开发不知道枚举值，测试不知道断言什么，DevOps 不知道告警挂在哪一态。
- 修改建议：PRD §3.2 新增一节明确：
  1. L0 状态枚举 + L1 状态枚举（各列举 4-5 个值 + 一句话语义）。
  2. 合法转移图（含 AC-10 回流路径）。
  3. 终态定义清单（哪些状态属于"不再处理"）。

**#A2（高）"可重试错误"和"不可重试错误"未划分清单，AC-07/AC-08 落不到代码**

- 关联：AC-07、AC-08、AC-09
- 问题：AC-07 列举了 7 种"临时错误"，但没说反面——什么算"永久错误"？例如：
  - LLM 返回 JSON 格式错误：算可重试还是不可重试？AC-07 把它列入临时错误，但实际上同一份输入再调一次大概率仍是同样错误（除非加随机种子或换 prompt）。
  - 链接读取 404：算"链接读取超时"吗？404 是永久错误。
  - LLM 速率限制：可重试，但退避策略应区别于网络超时。
  - 搜索服务认证失败 401：不可重试，但 AC-07 笼统写"搜索服务异常"。
- 风险：开发会自己拍脑袋分类，测试无法对齐验收，最终行为不可预期。AC-08「3 次 / 1min / 5min / 15min」退避对所有错误一刀切，对 429 限速可能过激（触发更严重限速），对 LLM JSON 错误可能浪费 token。
- 修改建议：PRD §3.2 给出两张表：
  1. **可重试错误清单**：网络超时 / 5xx / 429 / 连接重置 / LLM 服务 503 等，每条标注是否需要特殊退避（如 429 用 `Retry-After`）。
  2. **不可重试错误清单**：4xx 非 429 / LLM 解析错误（建议归入此类，由 prompt 自身问题排查）/ 链接 SSRF 拒绝 / 内容超长等。

**#A3（高）四类外部依赖（LLM / X 搜索 / Web 搜索 / 链接读取）的"具体使用什么"全部推迟到设计阶段，PRD 无法定稿**

- 关联：§5 前置依赖、§6.2 开放问题第 1/3 条、AC-12、AC-13
- 问题：PRD §6.2 把"Web 搜索、X 搜索具体用哪个服务"、"图片存储用什么方案"都标为"开放问题，由 Architect / Developer / DevOps 在设计阶段确认"。这违反基线规则：**PRD 阶段必须把前置依赖收敛清楚，设计阶段只做实现选型，不做范围决策**。当前写法实质上要架构师代 PM 做产品决策：
  - 是用 X 官方 Recent Search API（需 Basic 套餐起步）还是抓取式搜索？这两者成本差 1-2 个数量级。
  - 是用 Tavily / Serper / Google Custom Search 还是自建 SearXNG？这两者部署模式完全不同（外部 SaaS vs 自托管）。
  - 是直接 fetch + cheerio 还是用 Jina Reader / Firecrawl？前者免费但容易触发反爬，后者收费但稳定。
- 风险：架构师设计阶段做选型，会被开发/DevOps 推回"这是产品决策"；多走一轮 Review。
- 修改建议：PRD 应至少在 §5 前置依赖给出**候选清单 + 倾向选择 + 选择不确定时的兜底策略**。例如：
  - LLM：复用现有 OpenRouter / Claude（明确是哪个 endpoint）。
  - Web 搜索：候选 A、B、C，倾向 X；如 X 不可用降级为 Y。
  - X 搜索：候选 A、B，倾向 X。
  - 链接读取：候选 A、B，倾向 X；本期是否做 SSRF 防护。
  - 不要求一次锁定，但必须把候选范围 + 决策维度（成本/速率/部署复杂度）写明。

#### 中严重度

**#A4（中）评分四维输出口径与综合分公式潜在矛盾**

- 关联：AC-16、AC-17
- 问题：AC-16 要求 AI 输出 4 个 `1-5` 维度分；AC-17 要求按 `25%/35%/25%/15%` 权重计算 `1-10` 综合分。但：
  - 4 个 1-5 分加权计算后最大值是 `1×5×100%=5`，怎么映射到 `1-10`？是 `(weighted)/5 × 10` 还是 `weighted × 2`？
  - 这两个公式在边界值不一样：当所有维度分=1 时，前者=2 后者=2；当所有维度分=5 时，前者=10 后者=10；线性映射时一致。但 PRD 未明确，开发会拍脑袋。
  - 综合价值分是否四舍五入到整数？前端 AC-21 说"展示综合价值分"但未说精度。
- 修改建议：明确写出公式（如 `综合分 = round((d1×0.25 + d2×0.35 + d3×0.25 + d4×0.15) × 2, 1)`，结果保留 1 位小数 `1.0-10.0`），以及边界保护（如 AI 返回非数字时的默认值）。

**#A5（中）AC-19 五类标签的"标签来源、可枚举性、归一化"未定义**

- 关联：AC-19、§2.4、AC-14
- 问题：AC-19 要求 5 类标签分别输出但没说：
  - 是否有枚举闭集？例如"内容类型"是 `news/opinion/data/announcement` 这类闭集，还是 AI 自由生成？
  - "处理标签"是什么？是 L0 标签（`normal_candidate / high_priority_candidate / needs_context_candidate`）的延续，还是独立的 L1 处理结果标签？AC-04 用了同一词"标签"指 L0 输出，容易混淆。
  - "领域标签"和 INDEX 跨任务待办里 v0.5 的"领域标签管理后台"是否同一套？PRD §4.2「不做完整领域标签管理后台；L1 AI 标签按本迭代输出结构生成和展示」暗示本期 AI 自由生成，但前端如何对未知标签做颜色/分组？
- 修改建议：PRD §3.4 加一段定义五类标签：
  - 是闭集还是开集；
  - 与 L0 标签的关系；
  - 与现有 `sources.domain_tags / content_topics / source_role` 字段的关系（是否共享、是否互推、是否冲突时谁优先）。

**#A6（中）背景补全的"来源标签"展示规则与底层数据结构脱节**

- 关联：AC-14、AC-15、§2.4
- 问题：AC-14 列举 5 种补全来源（Source 信息 / 链接内容 / 库内相关新闻 / X 搜索 / Web 搜索），要求"抽屉展示对应来源标签"。但：
  - 是按段落标注（每句话挂一个来源）还是按章节标注（背景补全段落标一个混合来源列表）？前者要求 LLM 输出结构化引用（类似 RAG citation），实现成本极高；后者实现简单但用户无法精确追溯。
  - AC-15 又要求"区分已确认事实、合理推断、不确定点"，这要求 LLM 自分类置信度。和来源标签是正交两套元数据，还是合并成一个？
- 修改建议：PRD §3.3 明确：
  - 来源标签的粒度（句子级 / 段落级 / 章节级），优先推荐章节级以降低 LLM 输出结构复杂度。
  - AC-15 的"事实/推断/不确定"标签是用哪种载体表达（图标 / 文字前缀 / 段落标签），与 AC-14 来源标签共存的呈现方式。

**#A7（中）"库内相关新闻检索"算法策略未定义**

- 关联：AC-11、§6.2 开放问题第 2 条
- 问题：AC-11 强制"每条 L1 都执行库内检索"，但检索方式（关键词 ILIKE / pgvector 向量 / Elasticsearch 全文 / OpenAI embedding）会带来**架构层差异巨大**的方案：
  - 向量检索需要新增表存 embedding + 选 embedding 模型 + 决定何时更新。
  - 全文检索需要新建 `tsvector` 列 + GIN 索引或引入新服务。
  - ILIKE 简单但召回质量低，且 PG 性能不行。
- 这同样不是"设计阶段实现细节"，而是会决定**是否新增基础设施**和**是否额外烧 LLM token 做 embedding**。
- 修改建议：PRD 在 §5 前置依赖给出候选清单 + 倾向方案；如真要留到设计阶段，至少把"是否引入新基础设施（embedding 服务 / 全文索引）"的决策标准写明（如：日处理量 X 条以下用 ILIKE，以上才上向量）。

**#A8（中）空间图标上传的存储位置、文件名规范、清理策略未在 PRD 收敛**

- 关联：AC-26、AC-27、AC-28、§6.2 开放问题第 3 条
- 问题：§6.2 把"图片上传存储位置（本地静态目录、数据库引用、对象存储或其他）"标为"由 Architect / DevOps 在设计阶段确认"。但这同样是产品/部署决策不是架构选型：
  - 本地静态目录 → 部署回滚时文件可能丢失（v0.5 已踩过部署架构坑，参考 [`full-stack-deploy-handbook.md`](../knowledge/devops/full-stack-deploy-handbook.md) 软链接模式）。
  - 数据库 bytea → 拖慢 SELECT。
  - 对象存储 → 新增成本/账号/部署密钥。
- AC-27 要求"文件类型和大小限制"，但 PRD 没给具体阈值（MIME 白名单 / 最大 KB / 分辨率上限）。
- AC-28 说"上传/替换/移除后展示最新图标"，没说替换/移除是否要清理旧文件（避免长期占用磁盘）。
- 修改建议：PRD §3.6 补充：
  - 限制：MIME 白名单（如 `image/png, image/jpeg, image/webp`）+ 最大文件大小（建议 ≤ 500KB）+ 最大分辨率（建议 256×256，因为图标场景）。
  - 存储位置候选 + 倾向方案 + 兜底；明确替换/移除是否要清理旧文件。

#### 低严重度

**#A9（低）AC-25「不得用 mock 数据作为正式展示路径」与开发期 mock 兼容性未说清**

- 关联：AC-25
- 问题：禁止"正式展示路径"用 mock，但开发期、Storybook、Tester 联调时是否允许？建议措辞改为"生产环境构建不得包含 mock 数据"或"路由/页面在 prod 模式下不应回退到 mock"，避免开发期被卡。

**#A10（低）AC-23「不应出现独立全屏详情页入口」与未来可扩展性的关系**

- 关联：AC-23、§4.2
- 问题：本期不做详情页 OK，但 PRD 没说**抽屉是否预留"扩展到详情页"的入口**。例如抽屉头部是否需要一个分享/收藏/展开按钮的空槽位，避免后续迭代时再改路由结构。建议补一句"本期不做，但抽屉结构需为后续详情页扩展预留扩展位"或明确"本期保持最简结构，未来再说"。

**#A11（低）§2.6 覆盖页面清单与现有路由表对齐缺失**

- 关联：§2.6
- 问题：列举了 10 个覆盖页面（"全局导航和布局 / 新闻浏览页 / 管理页 / Source 详情页 / 告警/日志监控页 / 添加信息源抽屉 / 编辑/删除弹窗 / 统计卡片 / 空间/频道筛选 / 信息源库表格"），但现有 Vue 前端实际路由是 `/news`、`/admin`、`/admin/logs`、`/admin/sources/:id`、`/admin/alerts` 等（命名可能有出入）。PRD 没说每个页面对应当前哪条路由，UI 阶段会反复对齐。建议 PM 在 §2.6 加一张映射表「原型页面 → 当前 Vue 路由 → 重构后路由」，便于 UI 阶段直接接入。

#### 不阻塞的观察

- v0.5 已落地 `tasks` 表带 `max_attempts / attempt / run_after / last_error`，本期 L0/L1 重试机制可直接复用，AC-07/AC-08 在数据层很大程度上已经支持，是好基线。
- `raw_items.content` 已是 jsonb，存 X 原始推文 + L0 标签兼容（建议设计阶段考虑是否新增 `l0_meta jsonb` 字段还是塞进 content）。
- `processed_news.tags / entities / source_refs` 已是 jsonb 三件套，AC-19 五类标签和 AC-14 来源标签都能在不改表的情况下落（但建议设计阶段评估是否拆出 `processed_news_l1_meta` 单表以避免 jsonb 越塞越大）。
- ADR-001（drizzle generate + journal）已落地，本期任何 schema 变更必须走 `db:generate` 增量迁移、不能复制粘贴 baseline。

#### 总结

- 阻断项（#A1-#A3）属于"PRD 阶段必须收敛"的内容，设计阶段无法替 PM 决策。
- 中严重度（#A4-#A8）属于"PRD 应给方向、设计阶段做选型"，目前完全甩给设计阶段会导致 Architect / DevOps 在设计阶段被迫做产品决策。
- 低严重度（#A9-#A11）是表述完善和未来扩展位预留。
- 三条主线技术可行性 OK，没有架构红线问题；现有 v0.5 schema 和 worker 框架可作为良好基线。
- 等待 PM 汇总全部 5 方 R1 Review 后提交 R2；届时 Architect 复审。
