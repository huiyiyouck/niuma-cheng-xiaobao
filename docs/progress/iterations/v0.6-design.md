## 2. 数据模型

### 2.1 `raw_items` 扩展（L0/L1 状态字段）

新增列（v0.6 增量，不走 rename）：

```sql
-- 新增列
ALTER TABLE raw_items
  ADD COLUMN l0_status    varchar(30) NOT NULL DEFAULT 'pending',
  ADD COLUMN l0_label     varchar(50),            -- AC-04: normal_candidate / high_priority_candidate / needs_context_candidate
  ADD COLUMN l0_processed_at  timestamptz,
  ADD COLUMN l0_error     text,
  ADD COLUMN l1_status    varchar(30) NOT NULL DEFAULT 'not_started',
  ADD COLUMN l1_error     text,
  ADD COLUMN l1_attempt   integer NOT NULL DEFAULT 0,
  ADD COLUMN l1_next_retry_at  timestamptz,
  ADD COLUMN l1_processed_at  timestamptz;

-- 索引
CREATE INDEX IF NOT EXISTS ix_raw_items_l0_queue
  ON raw_items(l0_status, l1_status, published_at)
  WHERE l0_status = 'passed' AND l1_status = 'not_started';

CREATE INDEX IF NOT EXISTS ix_raw_items_l1_queue
  ON raw_items(l1_status, l1_next_retry_at, published_at)
  WHERE l1_status IN ('queued', 'retryable_failed');
```

**ADR-002**：L0/L1 状态落在 `raw_items` 双字段独立
- 方案 A（采用，推荐）：`raw_items.l0_status` + `raw_items.l1_status` 双字段
  - 优点：L0/L1 状态解耦，L1 重试不影响 L0 历史状态；单行查询无需 JOIN tasks 表
  - 代价：多 2 个索引
- 方案 B（否决）：`tasks` 表单字段承载
  - 理由：tasks 行是任务粒度，L0/L1 是信息粒度；一条 raw_item 产生 1 L0 task + 1 L1 task，L0 task completed 后 raw_item 的 L0 状态丢失，需额外查 tasks 历史才能追溯
- 方案 C（否决）：独立 `processing_states` 表
  - 理由：增加 JOIN，churn 与双字段相当；PRD §2.3 状态机要求 L0/L1 状态"独立且可追溯"，双字段满足

状态枚举映射（PRD §2.3 产品状态机 → schema 枚举值）：

```text
raw_items.l0_status:
  'pending'    ← PRD: L0 pending（原始信息已入库，尚未开始 L0 判断）
  'processing' ← PRD: L0 processing
  'skipped'    ← PRD: L0 skipped（终态）
  'passed'     ← PRD: L0 passed（已准备送入 L1）
  'failed'     ← PRD: L0 failed（终态，非重试失败——设 failed 表示已超过重试上限）
  'retryable'  ← 新增设计层：L0 失败可重试（transfer 图中 L0 failed → L0 pending 用此态标识）

raw_items.l1_status:
  'not_started'   ← PRD: L1 not_started
  'queued'        ← PRD: L1 queued
  'processing'    ← PRD: L1 processing
  'retryable_failed' ← PRD: L1 retryable_failed
  'final_failed'  ← PRD: L1 final_failed（终态）
  'completed'     ← PRD: L1 completed（终态）
```

**额外说明：L0 `retryable` 状态**
- PRD §2.3 状态机表中 L0 只有 `pending/processing/skipped/passed/failed` 5 态，但转移图中 `L0 failed → L0 pending / L0 processing` 暗示 L0 可重试。
- 设计层新增 `retryable` 状态：L0 执行失败但属于可重试错误时 → `l0_status = 'retryable'`，由新的 worker 轮询或 `l1_next_retry_at` 触发重试；达到重试上限后 → `l0_status = 'failed'`（终态）。
- 与 L1 的 `retryable_failed` 字段命名不对称但语义一致：L1 叫 `retryable_failed` 是因为 L1 多一个 `completed` 终态；L0 叫 `retryable` 是因为 L0 只有 `passed / skipped / failed` 三个终态，不需要 `retryable_failed` 区分"等待重试"和"最终失败"。

### 2.2 `processed_news` 扩展（L1 输出结构）

```sql
-- 新增列（全部 jsonb，非破坏性扩展）
ALTER TABLE processed_news
  ADD COLUMN translation     jsonb,   -- { zh: "中文翻译", original?: "原文" }
  ADD COLUMN context         jsonb,   -- ContextParagraph[] see §3.3
  ADD COLUMN analysis        text,    -- AI 分析评价文本
  ADD COLUMN score_total     numeric,   -- 1-10 保留 1 位小数
  ADD COLUMN score_dimensions jsonb,  -- { timeliness: {score, reason}, impact: {score, reason}, confidence: {score, reason}, clarity: {score, reason} }
  ADD COLUMN tags_v2         jsonb;   -- 五类标签结构 { domain: string[], entity: string[], event: string[], content_type: string[], processing: string[] }
```

**ADR-003**：新增字段全部 jsonb 增量扩展，不拆子表
- 方案 A（采用，多 jsonb 列）：`processed_news` 表上直接加 6 列 jsonb/text
  - 理由：v0.5 `processed_news` 已有 `tags / entities / source_refs / bullets` 4 个 jsonb 列，模式成熟；新增列全部是非结构化/半结构化数据，拆子表会增加 SELECT 复杂度
  - 代价：单行可能增长到 10-100KB，但 v0.5 月增长约 3000-15000 行，一年不到 2GB，PG jsonb 可以承受
- 方案 B（否决）：拆 `processed_news_l1_meta` 一对一子表
  - 理由：Developer PRD R1 已推荐（不阻塞观察），但经评估 v0.5 增长量级下拆表增加 JOIN 开销且无实质收益，不拆。
- 字段迁移说明：
  - `importance_score numeric`（v0.5 现存）保留不动；`score_total numeric` 是 v0.6 新增加权计算后的综合分字段；两者在 L0/L1 处理完成前分别为 `0` / `NULL`
  - `tags jsonb`（v0.5 现存，`string[]` 结构）保留不动；`tags_v2 jsonb` 是 v0.6 五类分类结构。v0.5 历史数据兼容：前端在 `tags_v2` 为 NULL 时降级为 `tags` 平铺数组作为 `processing` 类显示
  - `entities jsonb`（v0.5 现存，`any[]` 结构）保留不动；`translation / context / analysis / score_dimensions` 为完全新增字段

### 2.5 `alerts` type 扩展（AC-32）

PRD R2 AC-32 要求：外部依赖连续失败、L0/L1 队列长时间无进展、L1 final_failed 数量异常增长时应产生可见告警。

新增 type 枚举值（建议，设计阶段可调整）：

```text
'task_stale'              ← tasks.locked_by 卡住 > TASK_STALE_SECONDS
'external_dep_down'       ← 连续 N 条 L1 因同一外部依赖失败
```

v0.5 告警类型 `x_stream_disconnected / fetch_failure / zero_new / circuit_open / fetch_auth_failed` 不受影响。

Server 行为：

- 替换已有图片文件时先物理删除旧文件（AC-28b）
- 写入失败时保留原值，不损坏已有数据（AC-28a）

**数据来源 与 语义映射**（回应 UI R1 #A4）：

每个 count 的 SQL 语义：

```sql
-- completed = L1 completed
SELECT count(*) FROM raw_items
 WHERE source_id = $1
   AND l1_status = 'completed'
   AND (l1_processed_at > now() - interval '24h' OR l1_processed_at IS NOT NULL);

-- skipped = L0 skipped
SELECT count(*) FROM raw_items
 WHERE source_id = $1
   AND l0_status = 'skipped'
   AND (l0_processed_at > now() - interval '24h' OR l0_processed_at IS NOT NULL);

-- retryable_failed = L1 retryable_failed
SELECT count(*) FROM raw_items
 WHERE source_id = $1
   AND l1_status = 'retryable_failed'
   AND (l1_processed_at > now() - interval '24h' OR l1_processed_at IS NOT NULL);

-- final_failed = L1 final_failed（不包括 L0 failed——L0 failed 较少、日志查 L0 error 即可）
SELECT count(*) FROM raw_items
 WHERE source_id = $1
   AND l1_status = 'final_failed'
   AND (l1_processed_at > now() - interval '24h' OR l1_processed_at IS NOT NULL);
```

**为什么按 `l1_processed_at` 而不是 `published_at`**：窗口是"最近处理时间"维度，不是"信息发布"维度。

**为什么 `final_failed` 只包含 L1 不含 L0**：L0 failed 层数量极少（原始数据格式问题才会 L0 failed），归入手动排查场景；L1 final_failed 是"有价值但处理失败"的核心指标。

### 4.2 L0 Classifier（新增 Worker 模块）

**文件路径**：`server/src/worker/l0-classifier.ts`

**入参**：`raw_item_id: string`（通过 tasks 表 claim）

**处理逻辑**（PRD R2 AC-03/AC-04）：

```text
1. 读取 raw_items.content + sources.*（identity / domain_tags / attention_level）
2. 规则引擎判定（以下条件若命中→skipped）：
   a. content 文本为空或仅空白字符 → skipped
   b. content.Hash 与已处理的 raw_item.contentHash 重复 → skipped
   c. 纯 emoji（字母+数字占比 < 5%）→ skipped
   d. 纯转发无新增文本（content.retweet && !content.added_text）→ skipped
   e. 抽奖/招聘/无关广告（关键词正则匹配）→ skipped
3. LLM 判定（以下条件若规则引擎不跳过→调 LLM）：
   f. 与 Source 主题明显无关 → skipped
   g. 乱码（U+FFFD 高比例 / 不可猜测模式）→ skipped
4. 通过时：
   - l0_status = 'passed', l0_label = 'normal_candidate' / 'high_priority_candidate' / 'needs_context_candidate'
   - 创建 l1_process task：INSERT INTO tasks(type='l1_process', source_id, raw_item_id, status='queued', ...)
5. 失败（规则引擎 + LLM 都 fail）：
   - 可重试错误 → l0_status = 'retryable', 设 l0_error + 创建 l0_classify task 重试
   - 不可重试错误 → l0_status = 'failed'（终态）, 设 l0_error
6. 更新 l0_processed_at
```

**规则引擎优先**：规则引擎不走的 case（"与 Source 主题无关"需要语义理解）才走 LLM，以减少 LLM 调用量。

**L0 Label 选择策略**（PRD AC-04）：
- `high_priority_candidate`：Source attention_level = 'high' + 推文含关键词 / 高互动指标
- `needs_context_candidate`：推文含链接 / 含项目代号 / 含缩写
- `normal_candidate`：以上都不满足

#### L0 错误分类与重试（对应 PRD §3.2 三档表 + AC-08）

| 错误类型 | 示例 | L0 行为 |
|----------|------|---------|
| 可重试 | LLM 超时/5xx、网络错误 | `l0_status='retryable'`, 创建重试 task；3 次上限 [60s, 300s, 900s] |
| 不可重试 | raw_item 不可解析、source_type 未注册 | `l0_status='failed'`（终态）, 不重试 |
| 降级 | —（L0 无降级，跳过即终态或 passed 即进 L1） | — |

### 4.3 L1 Processor（扩展 v0.5 processor.ts）

**文件路径**：`server/src/worker/l1-processor.ts`（新建，非破坏 processor.ts）

**入参**：`raw_item_id: string`（通过 tasks 表 claim），`source_id: string`

**阶段分解**（5 个子阶段，串行，每个阶段失败按错误类型分类）：

#### 阶段 1：库内相关新闻检索（AC-11）

```text
策略：ILIKE 全文检索（当前处理量 100-500 条/日，不需要向量）
条件：每次必做
输入：raw_item 的标题/摘要关键词
输出：5 条相关 processed_news.title + summary
失败：记录"kb_search 异常"（不阻断——背景补全时基于 Source + LLM 知识继续）
```

SQL（ILKE 基础版）：

```sql
SELECT pn.id, pn.title, pn.summary, pn.published_at
FROM processed_news pn
JOIN raw_items ri ON ri.id = pn.raw_item_id
WHERE ri.source_id != $1   -- 排除当前 Source
  AND (pn.title ILIKE '%' || $2 || '%' OR pn.summary ILIKE '%' || $3 || '%')
  AND pn.published_at > now() - interval '7 days'
ORDER BY pn.importance_score DESC, pn.published_at DESC
LIMIT 5;
```

`$2`, `$3` 从 raw_item 的文本中提取关键词（取前 3 个单词/术语）；关键词提取方法：取 title 中非停用词的前 3 个有含义的 token（英文）或取 2-4 个汉字短语（中文）。

**是否同步执行**：同步。LLM 主调用（阶段 5）需要库内检索结果作为上下文，所以是 sync 的。单次检索耗时 < 50ms，可以接受。

#### 阶段 2：链接读取（AC-12）

```text
条件：推文 content.url / source_item_url 存在
工具：fetch + HTML text extraction（cheerio 或 built-in Node 文本抽取）
超时：10s
失败：记录 error, 标记 `sources: ["link"]` 不存在于该段落的 source 列表
       不阻断 L1（AC-12 明确"不阻塞"）
```

#### 阶段 3：外部搜索（AC-13）

```text
条件：LLM 判断 needs_context=true（阶段 4 内完成判断，合并在 prompt 内，
       由 LLM 在输出的 JSON 中标记 needs_context）
触发：needs_context=true → X 搜索 + Web 搜索
      否则跳过

X 搜索：搜索该 user 最近 5 条推文（使用 X API v2 Recent Search 或抓取式搜索）
Web 搜索：搜索关键词（使用 Tavily / Serper / Google Custom Search 之一，
          设计阶段暂不锁定具体服务，PRD §5 边界表已定义"可选增强，失败不阻断"）

失败：记录 error，不阻断 L1
```

**关于 X 搜索和 Web 搜索的触发条件建议细分**（Architect R2 观察 4）：
- X 搜索补全 Source 自身上下文，在 `needs_context=true && 推文内容涉及该账号历史行为或立场` 时最有价值
- Web 搜索补全外部上下文，在 `needs_context=true && 推文引用外部事件/项目/概念` 时最有价值
- 初步实现可以两个都发（成本低时），第一个版本简化为 needs_context=true 时两个都触发，后续优化

#### 阶段 4：LLM 主调用（AC-05/AC-16/AC-19）

这是 L1 核心产出。使用 v0.5 `llm.ts` 的现有基础设施（`processLLM`）。

**LLM 调用策略**（Developer PRD R1 #D5 关闭方案）：
- **单次调用**：将所有上下文（库内检索结果、链接内容、X/Web 搜索摘要、Source 身份信息、原始推文）拼入一个 prompt，一次返回所有产出
  - 理由：v0.5 路线已稳定；v0.5 同场景使用单次 LLM + `extractFirstJsonObject`，成功率约 90%
  - 风险：JSON 体量大（11+ top-level key）可能增加解析失败率
  - 兜底：按 PRD AC-07/§3.2 "AI 输出连续结构不合法" → 不可重试的错误档位，N=2 次后进入 final_failed

**Prompt 结构**（新增超参数模板，不随代码 hardcode）：

```
你的角色：信息分析助手
输入：
- Source 身份：{source.identity}（{source.domain_tags}）
- 原始推文：{content}
- 库内相关新闻：{kb_results}
- 链接内容：{link_content | "无"}
- 搜索摘要：{search_summary | "无"}

请输出以下 JSON：
{
  "title": "中文标题",
  "summary": "中文摘要（80-200字）",
  "translation": { "zh": "中文翻译", "original": "原文" },
  "context": [
    {
      "text": "一段背景补全文本",
      "confidence": "fact | inference | uncertain",
      "sources": ["source" | "link" | "library" | "x_search" | "web_search"]
    }
  ],
  "analysis": "AI 分析与评价",
  "scores": {
    "timeliness": { "score": 1-5, "reason": "..." },
    "impact": { "score": 1-5, "reason": "..." },
    "confidence": { "score": 1-5, "reason": "..." },
    "clarity": { "score": 1-5, "reason": "..." }
  },
  "tags": {
    "domain": ["标签"],
    "entity": ["标签"],
    "event": ["标签"],
    "content_type": ["标签"],
    "processing": ["标签"]
  },
  "needs_context": true | false
}
```

**综合分计算（服务端，不由 AI 直接决定）**：

```text
weighted = (scores.timeliness × 0.25 + scores.impact × 0.35 + scores.confidence × 0.25 + scores.clarity × 0.15)
score_total = Math.round(weighted × 2 × 10) / 10   -- 1.0-10.0 1位小数
```

**后处理**：JSON 解析失败 → 按 AC-07/§3.2 错误分类表处理（可重试 2 次 → 仍失败则 final_failed）

#### 阶段 5：写入 + 新闻位置分发

```text
1. INSERT/UPDATE processed_news（通过 raw_item_id ON CONFLICT 去重）
   - title, summary, translation, context, analysis, score_total, score_dimensions, tags_v2
   - source_refs 扩展为包含库内检索/链接/搜索来源 URI
   - published_at 沿用 raw_items.published_at（原始时间）
2. raw_items.l1_status = 'completed', l1_processed_at = now(), l1_attempt = attempt
3. 创建 news_positions 记录（与 v0.5 processor.ts 一致——查找该 Source 的 display_position 并 fan-out）
```

### 4.4 Dispatcher 改造（type 分支退避）

v0.5 `dispatcher.ts` 的 `requeueTask` 当前使用线性退避（`delaySeconds = min(300, 10 * (tries + 1))`，max 5 次）。

**改造后** —— 按 `tasks.type` 分支退避（PRD AC-08 "不影响既有任务类型"）：

```ts
const BACKOFF_CONFIG: Record<string, { maxAttempts: number; backoff: number[] }> = {
  // v0.5 既有
  fetch:   { maxAttempts: 5, backoff: [10, 20, 40, 80, 160] },      // 线性退避（接近原有）
  process: { maxAttempts: 5, backoff: [10, 20, 40, 80, 160] },      // 同 fetch

  // v0.6 新增
  l0_classify: { maxAttempts: 3, backoff: [60, 300, 900] },         // 1min / 5min / 15min（PRD AC-08）
  l1_process:  { maxAttempts: 3, backoff: [60, 300, 900] },         // 同上
  l1_retry:    { maxAttempts: 1, backoff: [0] },                    // 手动重试不自动重试
};
```

**`requeueTask` 改造要点**：

```ts
async function requeueTask(conn: PoolClient, task: any, lastError: string): Promise<void> {
  const attempt = parseInt(task.attempt || "0");
  const cfg = BACKOFF_CONFIG[task.type] || BACKOFF_CONFIG.process;  // 默认用 process 配置

  if (maxAttempts > 0 && attempt >= maxAttempts) {

    } else if (task.type === 'l0_classify') {
      await setL0Failed(conn, task);        // 更新 raw_items.l0_status = 'failed'
    }
    await finishTask(conn, task.id, "failed", lastError);
    return;
  }
  const delay = cfg.backoff[Math.min(attempt - 1, cfg.backoff.length - 1)];
```

### 4.6 监控告警（AC-32 / §3.7）

```text
  → 验证 MIME / 大小 / 空间存在

  → 更新 DB channel_spaces.icon_url + icon_type = 'image'
  → 返回 { icon_url, icon_type }
  → 前端更新 SpaceIcon 组件展示

  → DELETE /v1/spaces/:id/icon
  → 删除磁盘文件
  → 更新 DB: icon_url=NULL, icon_type='emoji'（保留 icon 字段原值作为回退）
```

## 7. 风险和取舍

### 7.1 设计决策保留（ADRs）

#### ADR-005：图标上传存储选型

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| A. 后端持久目录 + nginx 反代（采用, 推荐） | 代码分离、nginx 缓存可控、备份独立 | 需要修改 nginx 配置、部署需同步 | — |
| B. DB bytea | 统一备份、回滚无文件残留 | SELECT 拖慢、上传大图跨网络传输加倍 | 图标是静态文件不是数据 |
| C. 对象存储（S3/minio） | 高可用、无磁盘占满风险 | 新增账号/密钥/部署复杂度、需改 nginx 反代 | v0.5 项目规模不需要 |

**最终方案 A**：持久目录 `/var/lib/niuma-news/uploads/`（见 §4.7）

#### ADR-006：库内检索走 ILIKE 基础版，不上向量

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| A. ILIKE 基础版（采用） | 零新依赖、零新 infrastructure、5ms-50ms | 召回质量低、只匹配关键词 | 当前 100-500 条/日规模够用 |
| B. pgvector + embedding | 召回质量高、语义而非词匹配 | 新增 embedding 调用成本 + DB 500MB+ + 迁移脚本 | 在下个量级（日 > 1000 条）时再评估 |
| C. Elasticsearch 全文 | 高质量中文分词、可扩展 | Docker 部署 + 系统资源占用 + 索引同步 | 作为一个人的项目过于重量级 |

- 优先级：中。AC-28a 三种异常路径无设计层兜底会让 Tester 测试时无对应物，实施阶段开发各自拍脑袋

**#T9（中）§4.4 dispatcher 改造的 `BACKOFF_CONFIG.l1_retry: { maxAttempts: 1, backoff: [0] }` 与 PRD AC-08「重试 3 次退避 [60, 300, 900]」语义可能冲突**

- 关联：§4.4 BACKOFF_CONFIG 表、PRD R2 AC-08、AC-31 手动重试入口、`POST /v1/l1-tasks/:task_id/retry`
- 现状：
  - PRD R2 AC-08 「自动重试最多 3 次，退避间隔为 1 分钟、5 分钟、15 分钟」—— 描述自动重试
  - AC-31 / `POST /v1/l1-tasks/:task_id/retry` —— 描述手动重试
  - §4.4 BACKOFF_CONFIG `l1_retry: { maxAttempts: 1, backoff: [0] }` —— 注释「手动重试不自动重试」
- 问题：
  - 手动重试创建的新 task type 是 `l1_retry`（设计文档 §3.2 POST endpoint 说「创建新 task 或复用旧 task 行重置」），但 `l1_retry` maxAttempts=1 意味着手动重试如果失败，**就不再走 AC-08 的 3 次自动重试**
  - 但 Owner 期望可能是「手动重试触发后还能享受 AC-08 的自动重试保护」（毕竟用户都按了重试按钮）
  - Architect R2 #A13 提到 L0/L1 状态对称化，但 §4.4 把"手动重试"作为独立 type 与自动重试分开——设计文档没说理由
- Tester 视角问题：
  1. 测试 AC-31 「手动重试入口」：触发后 task.attempt=0、status='queued'。如果实施阶段按 type='l1_retry' 创建新 task，maxAttempts=1 意味着失败一次即 final_failed
  2. 但 PRD AC-08 描述「自动重试 3 次」是否包括「Owner 按了重试后又开始数 3 次」？设计文档无答案
- 修改建议：§4.4 BACKOFF_CONFIG 或 §3.2 POST endpoint 说明：
  - 推荐方案 A：手动重试创建的新 task type 是 `l1_process`（不是 `l1_retry`），maxAttempts=3 与自动重试一致；`l1_retry` 这个 type 不引入（避免歧义）
  - 推荐方案 B：保留 `l1_retry` type 但 maxAttempts=3，与 `l1_process` 一致；用 `l1_retry` 仅是 type 标记便于在监控页区分「自动触发 vs 手动触发」
- 优先级：中。AC-31 实施时如果按 maxAttempts=1，Owner 体验会很差

#### 低严重度（3 条）

**#T10（低）§2.1 raw_items 索引 `ix_raw_items_l0_queue` 的 WHERE 条件包含 `l0_status = 'passed' AND l1_status = 'not_started'`，索引名误导**

- 关联：§2.1 索引定义
- 现状：

```sql
CREATE INDEX IF NOT EXISTS ix_raw_items_l0_queue
  ON raw_items(l0_status, l1_status, published_at)
  WHERE l0_status = 'passed' AND l1_status = 'not_started';
```

- 问题：索引名叫 `ix_raw_items_l0_queue` 暗示是 L0 队列索引，但 WHERE 条件实际筛选的是「L0 已通过、L1 未开始」即 **L0 → L1 过渡候选集**（待创建 l1_process task 的 raw_items）—— 真实 L0 队列应该是 `l0_status = 'pending'`
- Tester 视角：测试 `claimTask(type='l0_classify')` 性能时按索引名找索引会找错条件
- 建议：改名为 `ix_raw_items_l0_to_l1_transition` 或 `ix_raw_items_pending_l1`

**#T11（低）§3.2 `POST /v1/l1-tasks/:task_id/retry` 入参语义模糊：`task_id` vs `raw_item_id`**

- 关联：§3.2 该 endpoint Server 行为
- 现状：endpoint 参数是 `task_id`（对应 tasks 表）；Server 行为「重置 raw_items.l1_status='queued'」需要从 task_id JOIN 找到 raw_item_id
- Tester 视角：UI spec §6.5 提到「`POST /v1/l1-tasks/:task_id/retry`」时 task_id 是已有 task 的 id —— 但 raw_item 可能有多个历史 task（多次重试）。Tester 测试时用哪个 task_id？最后一次失败的？任意一次？
- 建议：§3.2 加一句「task_id 必须是该 raw_item 当前最近一次 status IN ('failed','retryable_failed','final_failed') 的 task」或改入参为 `raw_item_id`

**#T12（低）§4.3 阶段 4 LLM 调用「单次调用」+ JSON 解析失败重试 N=2 与 PRD R2 AC-07/AC-08 退避 [60, 300, 900] 时间表 N=3 不一致**

- 关联：§4.3 阶段 4、PRD R2 AC-07 / AC-08、§4.4 BACKOFF_CONFIG
- 现状：
  - §4.3 阶段 4「按 AC-07/§3.2 错误分类表处理（可重试 2 次 → 仍失败则 final_failed）」
  - PRD R2 AC-08 「自动重试最多 **3 次**」
  - §4.4 BACKOFF_CONFIG `l1_process: { maxAttempts: 3, backoff: [60, 300, 900] }`—— 与 PRD 一致
- 问题：§4.3 阶段 4 文字写 「N=2」与 §4.4 配置 maxAttempts=3 不一致
- 建议：§4.3 阶段 4 改为「N=3，与 §4.4 BACKOFF_CONFIG 一致」或显式说「JSON 解析失败有更短的重试上限 N=2（与 LLM 服务错误的 N=3 不同）」并在 §4.4 BACKOFF_CONFIG 加 `l1_process_json_retry` 子配置
