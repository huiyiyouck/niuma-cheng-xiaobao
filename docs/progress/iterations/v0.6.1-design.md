## 1. 概述

### 1.1 范围

v0.6.1 在 v0.6 全栈基线上做架构调整。核心变化：**AI 处理从 HTTP 同步调用改为数据库契约边界异步解耦**。

| 维度 | v0.6 现状 | v0.6.1 设计 |
|------|-----------|-------------|
| AI 调用方式 | HTTP 同步（`ai-hub.ts` → `/v1/runs/news-l1`） | 数据库契约（ai_worker 轮询 raw_items 状态） |
| 链路模式 | xiaobao 内置 L1 + AI Hub HTTP 双引擎 | xiaobao 仅标记状态 + 内建 L1 兜底；AI Hub 改为独立 worker 读库 |
| 状态机 | `l0_status` + `l1_status` 双字段（5 值） | 扩展 `l1_status` 枚举，新增 `process_type` 区分 direct/ai |
| 任务调度 | `tasks` 表复用 + claim + reclaim | 保留 `tasks` 表机制，新增 `l1_ai_process` type |
| 权限模型 | 单数据库用户（news） | 新增 `ai_worker` 数据库用户 + 列级 GRANT |
| 前端展示 | L1 完成后统一展示 | 按 `process_type` + `l1_status` 分层展示（直显/处理中/富展示） |

**设计覆盖**：
1. 数据模型变更（`raw_items.process_type` + `l1_status` 枚举扩展 + 索引调整）
2. 数据库契约边界（`ai_worker` 角色 + GRANT/REVOKE + 列级权限）
3. 核心流程（direct/ai 分流 + L1 claim 标记 + AI worker 轮询写回 + 卡死回收）
4. API 契约（前端接口变更 + 管理侧 AI 统计）
5. 内建 L1 兜底保留（xiaobao 侧 builtin/agent 引擎保留，默认关闭）
6. 迁移方案 + 灰度切换 + 回滚方案
7. 运维告警 + dry-check + 部署验证清单

**不覆盖（PRD §4.2 已明确排除）**：
- L2 事件追踪 / 反馈评论 / 独立详情页 / 深度时间线分析
- 翻译 API 接入（由 AI 侧在深度解析时一并处理）
- 新增前端页面（仅现有 NewsPage 展示分层）

### 1.2 设计前提

- 基于 v0.6 设计文档已落地、v0.6.1 PRD R2 已定稿
- **schema 迁移路径**：v0.6 部署经验确认生产/测试库 drizzle 迁移元数据脱轨，当前实际用人工 SQL 部署。v0.6.1 **延续人工 SQL 迁移**（不走 drizzle-kit generate），避免元数据冲突导致迁移失败。drizzle schema.ts 仍同步更新以保持类型定义一致，但生产迁移用人工 SQL。（#D4 修复）
- `raw_items` 双字段状态机（`l0_status` + `l1_status`）延续 ADR-002
- `processed_news` 表 jsonb 增量扩展延续 ADR-003
- `tasks` 表复用延续 ADR-004
- xiaobao 侧保留内建 L1 处理能力（builtin/agent 引擎）作为兜底，默认由 `ai_worker` 外部处理

## 2. 数据模型

### 2.1 `raw_items` 扩展

**新增列（v0.6.1 增量）**：

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `process_type` | `varchar(20)` | NOT NULL, DEFAULT 'ai' | 处理类型：`direct`（直显类）/ `ai`（AI 处理类）。对应 PRD AD-03 直显类也创建 processed_news |

**`l1_status` 枚举（现有值保留兼容，无需修改枚举定义）**：

| 现有值（v0.6） | 保留？ | 新语义 | PRD AC-07 对应 |
|---------------|--------|--------|----------------|
| `not_started` | ✅ 保留 | 未开始处理 | — |
| `queued` | ✅ 保留 | 已入队待处理（AI 类） | `pending`（PRD 产品语义用 `pending`，技术实现复用 v0.6 现有 `queued` 枚举值，两者等价）（#PM-2 / #DD11 修复） |
| `processing` | ✅ 保留 | 处理中（AI 类，被 ai_worker claim） | `processing` |
| `completed` | ✅ 保留 | 处理完成（AI 类富展示 / direct 类直显完成） | `completed` |
| `retryable_failed` | ✅ 保留 | 可重试失败 | `retryable_failed` |
| `final_failed` | ✅ 保留 | 最终失败 | `final_failed` |

- `direct` 类：`l1_status = 'completed'` 表示直显完成（基础展示）

### 2.3 `news_positions` 表（无 DDL 变更，写回职责明确）

**写回职责边界（ADR-006 / PRD AD-02）**：

| 操作 | xiaobao 侧 | ai_worker 侧 |
|------|-----------|--------------|
| `processed_news` INSERT/UPDATE | ✅ 直显类创建 | ✅ AI 类写入结果 |
| `news_positions` INSERT | ✅ 触发器自动关联 | ❌ 无权限（由 SECURITY DEFINER 触发器代写） |
| `raw_items.l1_status` 更新 | ✅ claim/标记 | ✅ 更新结果状态 |

**AI 类新闻的 news_positions 关联时机**：

> 设计选择：**SECURITY DEFINER 触发器方案**。理由：实时性好，不增加 worker 逻辑复杂度，数据库层保证一致性。触发器函数用 `SECURITY DEFINER` 以创建者（schema owner）身份执行，ai_worker 不需要 `news_positions` 的 INSERT 权限。（#D1 修复）

```sql
-- 触发器函数：processed_news 插入后自动关联 display_positions
-- SECURITY DEFINER：以函数创建者（schema owner = news 用户）身份执行
-- search_path 锁定防止 search_path 注入
CREATE OR REPLACE FUNCTION auto_link_news_position()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
BEGIN
  INSERT INTO news_positions (news_id, position_id, created_at)
  SELECT NEW.id, dp.id, now()
  FROM display_positions dp
  JOIN raw_items ri ON ri.id = NEW.raw_item_id
  WHERE dp.source_id = ri.source_id
    AND dp.enabled = true
    AND dp.deleted_at IS NULL
  ON CONFLICT (news_id, position_id) DO NOTHING;
  RETURN NEW;
END;
$$;

-- 触发器
DROP TRIGGER IF EXISTS trg_processed_news_auto_link ON processed_news;
CREATE TRIGGER trg_processed_news_auto_link
AFTER INSERT ON processed_news
FOR EACH ROW
EXECUTE FUNCTION auto_link_news_position();
```

> 注意：添加触发器后，`processor.ts` 中现有的手动 `news_positions` 创建代码（L88-106）应**移除**，避免冗余执行。触发器已覆盖所有 processed_news INSERT 场景（直显类 + AI 类）。（#DD10 修复）

### 2.5 数据库角色与权限（ADR-008）

**新增角色**：`ai_worker`

**GRANT 范围（最小权限原则，已修复 #DD2 / #DD5 / #DD6）**：

```sql
-- 创建角色
CREATE ROLE ai_worker WITH LOGIN PASSWORD '${AI_WORKER_DB_PASSWORD}';

-- 连接权限
GRANT CONNECT ON DATABASE ${DB_NAME} TO ai_worker;
GRANT USAGE ON SCHEMA public TO ai_worker;

-- 安全加固：禁止 ai_worker 在 public schema 建表（#D8 修复）
REVOKE CREATE ON SCHEMA public FROM ai_worker;

-- raw_items：只读指定列 + 可更新 l1_status / l1_error / l1_processed_at / l1_attempt
-- 注意：language 列在 processed_news 上，不在 raw_items 上（#DD5 修复）
GRANT SELECT (id, source_id, content, published_at, l0_status, l1_status, l1_attempt, process_type)
  ON raw_items TO ai_worker;
GRANT UPDATE (l1_status, l1_error, l1_processed_at, l1_attempt)
  ON raw_items TO ai_worker;

-- processed_news：可读写（AI 类结果写入）
GRANT SELECT, INSERT, UPDATE
  ON processed_news TO ai_worker;

-- sources：只读（获取 source_identity / domain_tags 等元数据）
GRANT SELECT (id, type, identity, config) ON sources TO ai_worker;

-- tasks：可 claim / 更新状态（#DD2 修复：追加 updated_at 列）
GRANT SELECT, UPDATE (status, locked_by, locked_at, attempt, updated_at, last_error, last_error_kind)
  ON tasks TO ai_worker;

-- 注意：processed_news.id 是 uuid defaultRandom()，不需要序列权限（#DD6 修复）
```

**REVOKE / 禁止项**：

```sql
-- 禁止 ai_worker 写 news_positions（由 SECURITY DEFINER 触发器代写）
REVOKE INSERT, UPDATE, DELETE ON news_positions FROM ai_worker;

-- 禁止 ai_worker 访问 source_states / alerts / admin 相关表
REVOKE ALL ON source_states FROM ai_worker;
REVOKE ALL ON alerts FROM ai_worker;
REVOKE ALL ON channel_spaces FROM ai_worker;
REVOKE ALL ON display_positions FROM ai_worker;
```

> 说明：`display_positions` 禁止直接访问，ai_worker 不需要知道 position 信息，processed_news 关联由 SECURITY DEFINER 触发器自动完成。

**查询架构改造（#DD3 修复）**：

```sql
-- 改造后：以 raw_items 为主表，LEFT JOIN processed_news
SELECT DISTINCT ON (ri.id)
  ri.id AS raw_item_id, ri.process_type, ri.l1_status,
  pn.id, pn.title, pn.summary, pn.language, pn.translation, pn.context,
  pn.analysis, pn.score_total, pn.score_dimensions, pn.tags_v2,
  pn.bullets, pn.tags, pn.entities, pn.importance_score, pn.source_refs,
  s.display_name AS source_name, s.id AS source_id
FROM raw_items ri
JOIN news_positions np ON np.news_id = pn.id   -- 仍需 JOIN news_positions 过滤
JOIN display_positions dp ON dp.id = np.position_id
LEFT JOIN processed_news pn ON pn.raw_item_id = ri.id
JOIN sources s ON s.id = ri.source_id
WHERE s.paused = false
  -- 只返回有关联 position 的（processed_news 存在时通过触发器已关联，
  -- AI 处理中无 processed_news 也需要返回，因此需要额外处理）
```

> **设计选择**：AI 处理中的新闻（`l1_status IN ('queued', 'processing', 'retryable_failed')`）也返回（对应 PRD AC-06 不丢失直显）。前端按 `l1_status` 展示占位态。原文标题/摘要从 `raw_items.content` 提取，不依赖 `processed_news`。

**实现方案（三选一，推荐方案①）**：

### 4.3 AI Worker 轮询与 Claim 流程

> **以下为 ai_worker 侧参考实现，不在 xiaobao 交付范围内。xiaobao 侧仅需保证数据库契约（表结构、权限、状态枚举）正确。**（#PM-6 修复）

ai_worker 主循环（伪代码）：

```typescript
async function aiWorkerTick(conn: PoolClient, workerId: string) {
  // 1. Claim 一个 l1_ai_process task
  const task = await claimTask(conn, workerId, 'l1_ai_process');
  if (!task) return; // 无任务，下一轮

  // 2. 更新 raw_items.l1_status = 'processing'
  await conn.query(
    "UPDATE raw_items SET l1_status = 'processing' WHERE id = $1",
    [task.raw_item_id]
  );

  try {
    // 3. 读取 raw_item 内容（language 不在 raw_items 上，在 processed_news 上）
    const rawItem = await conn.query(
      "SELECT id, source_id, content, published_at FROM raw_items WHERE id = $1",
      [task.raw_item_id]
    );

    // 4. 读取 source 元数据
    const source = await conn.query(
      "SELECT id, type, identity, config FROM sources WHERE id = $1",
      [task.source_id]
    );

    // 5. AI 深度解析（多语言输入 → 中文输出）
    const result = await aiDeepParse(rawItem, source);

    // 6. 写入 processed_news（UPDATE 覆盖占位记录）
    //    注意：processed_news 没有 updated_at 列（#DD1 修复）
    await conn.query(
      `UPDATE processed_news SET
         title = $2, summary = $3, language = $4,
         translation = $5, context = $6, analysis = $7,
         score_total = $8, score_dimensions = $9, tags_v2 = $10
       WHERE raw_item_id = $1`,
      [rawItem.id, result.title, result.summary, 'zh',
       JSON.stringify(result.translation), JSON.stringify(result.context),
       result.analysis, result.scoreTotal,
       JSON.stringify(result.scoreDimensions), JSON.stringify(result.tagsV2)]
    );

    // 7. 更新 raw_items 状态
    await conn.query(
      "UPDATE raw_items SET l1_status = 'completed', l1_processed_at = now(), l1_attempt = $2 WHERE id = $1",
      [task.raw_item_id, task.attempt]
    );

    // 8. 完成 task
    await finishTask(conn, task.id, 'completed');

  } catch (err) {
    // 9. 失败处理：判断是否可重试
    const isRetryable = classifyErrorRetryable(err);
    const newStatus = isRetryable ? 'retryable_failed' : 'final_failed';

    await conn.query(
      "UPDATE raw_items SET l1_status = $2, l1_error = $3, l1_attempt = l1_attempt + 1 WHERE id = $1",
      [task.raw_item_id, newStatus, String(err.message).slice(0, 500)]
    );

    if (isRetryable) {
      await requeueTask(conn, task.id, 'l1_ai_process', err.message);
    } else {
      await finishTask(conn, task.id, 'failed', err.message);
    }
  }
}
```

### 4.4 卡死回收（复用 ADR-004）

**现有 `reclaimStaleTick` 完全复用**（`server/src/worker/reclaim.ts`），无需修改。

回收规则：
- `tasks.status = 'running'` 且 `locked_at < now() - AI_STALE_TIMEOUT_MS` 且 `attempt < max_attempts` → 重置为 `queued`
- 超 max_attempts → 标记 `failed`

回收后：
- `l1_ai_process` task 重新进入队列，可被下一个 ai_worker claim
- `raw_items.l1_status` 保持 `processing`（由 ai_worker 重新 claim 后再次更新，或由 reclaim 同步更新为 `queued`）

**补充**：reclaim 时同步更新 raw_items.l1_status：

```typescript
// 在 reclaimStaleTick 中追加：
await conn.query(
  `UPDATE raw_items SET l1_status = 'queued'
   WHERE id IN (
     SELECT raw_item_id FROM tasks
     WHERE status = 'queued'
       AND type = 'l1_ai_process'
       AND raw_item_id IS NOT NULL
       AND l1_status = 'processing'
   )`,
);
```

**连接池配置（#D6 修复）**：

- 部署前 dry-check 必须包含 `SHOW max_connections;` 核验
- 两侧连接数总和上限：news-api + ai_worker < max_connections * 0.8

### 6.4 回滚方案（对应 PRD §6.6，#D10 修复）

**可回滚**：
- `AI_INTEGRATION_MODE=http`（秒级生效）→ 切回 HTTP 模式，人工处理 `queued`/`processing` 状态任务
- `L1_ENGINE=builtin` → 走内建 L1 兜底
- DDL 回滚：删除新增列/索引/触发器/角色

**不可回滚**：
- 无。本期无破坏性 DDL（仅 ADD COLUMN / CREATE INDEX / CREATE TRIGGER / CREATE ROLE），均可逆向操作。

**回滚步骤**：
1. 切 `AI_INTEGRATION_MODE=http`（秒级生效）
2. 人工处理 `queued`/`processing` 状态任务：`UPDATE raw_items SET l1_status = 'completed' WHERE l1_status IN ('queued', 'processing') AND process_type = 'ai'`（标记为已完成，前端展示原文占位）
3. 如需彻底回退代码：部署 v0.6 版本
4. 如需彻底回退 DDL：执行回滚 SQL（DROP COLUMN / DROP ROLE）
5. 回滚后 `process_type` 列保留（v0.6 代码忽略该列，DEFAULT 'ai' 不影响）
6. 回滚后 `processed_news` 中 AI 生成数据保留（前端按 `l1_status` 展示，不丢失）
7. `ai_worker` 角色可保留（不删除，仅停用服务）

## 7. 风险和取舍

### 7.1 风险清单（#PM-7 修复：补充产品风险）

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|

| 触发器性能影响 | 低 | 中 | 单条 INSERT 触发，量级小；可压测验证 |
| 列级 GRANT 配置错误导致 ai_worker 无法操作 | 中 | 高 | 部署前 dry-check + 健康检查 SQL |
| 历史数据回填期间锁表 | 低 | 中 | 分批更新 + 低峰执行 |

| 前端展示分层逻辑复杂 | 低 | 低 | 组件化封装 + 状态枚举集中管理 |
| 前端展示分层引入新视觉元素（解析中/失败角标）可能增加用户认知成本 | 低 | 低 | 角标设计低调不抢眼、只在 AI 类新闻显示、文案清晰（"解析中"/"解析失败"） |

### 7.2 取舍说明

1. **触发器 vs Worker 关联**：选择 SECURITY DEFINER 触发器（实时性好，不增加 worker 复杂度），牺牲一点数据库 CPU
2. **process_type 单列 vs 独立表**：选择单列（ADR-007，最小改动），牺牲一点查询灵活性
3. **内建 L1 保留 vs 删除**：选择保留（ADR-009，兜底保险），牺牲一点代码维护成本
4. **AI 处理中也返回 vs 不返回**：选择返回（AC-06 不丢失），增加一点前端复杂度
5. **ai-hub.ts 保留 vs 删除**：选择保留为灰度回退路径，2 个迭代后删
6. **占位 processed_news vs 查询改造**：选择占位方案（方案①），查询改造量小
