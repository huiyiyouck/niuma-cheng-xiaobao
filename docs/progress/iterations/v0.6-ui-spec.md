### 1.3 关键任务流程

#### 浏览高价值新闻

1. 进入 `/news`，统计卡片显示今日 L1 completed 数 + 总 L1 completed 累计
2. 选择空间 Pill → 选择频道 Pill → 看新闻列表
3. 点击新闻卡片 → 右侧滑出 480px 抽屉
4. 抽屉展示 6 段：摘要 / 翻译 / 背景补全（含来源+可信度） / AI 分析 / 评分（默认折叠 4 维） / 5 类标签
5. 关闭抽屉：点蒙层 / 点 × / 按 ESC

#### 创建空间 + 上传图标

1. 进入 `/admin`，默认 Tab 「空间管理」
2. 点击「+ 新建空间」卡片 → 弹出 SpaceEditDialog
3. 输入空间名 + 描述
4. 图标区：可选填 emoji 或点击「⬆ 上传图片」上传 PNG/JPG ≤ 1MB
5. 保存 → Toast 提示创建成功 → 空间卡片显示
6. 双击空间卡片 → 同一弹窗回填数据 → 可编辑或替换/移除图标

#### 查看 L0/L1 处理状况

1. 进入 `/monitoring`，默认 Tab 「告警」
2. 切换到 Tab 「日志」可看抓取/Worker/Stream/API 日志
3. 进入 `/sources/:id`，左栏底部「最近一周新闻」时间轴下方新增「L0/L1 处理状态计数」区块
4. 区块显示：completed N / skipped N / retryable_failed N / final_failed N（四色徽章）
5. 点击 retryable_failed 数 → 跳转到 `/monitoring?tab=logs&source=:id&level=ERROR`

#### 三路径新增信息源

1. 路径 A：`/admin` 信息源库 Tab → 表格右上「+ 添加信息源」→ AddSourceDrawer
2. 路径 B：`/admin` 空间管理 Tab → 选中某频道 → 频道列表右上 「+ 添加 Source」→ AddSourceDrawer（预填空间+频道）
3. 路径 C：`/sources/:id` 右栏「展示位置」→ 「+ 添加位置」→ AddSourceDrawer（预填 Source ID）

> 三路径都打开同一个 AddSourceDrawer 组件，预填参数不同。这是 v0.6 新增的第三入口（C）。

## 9. 风险和遗留

### 9.1 已知风险

- **R1（中）**：原型 5 类标签只画 2 类、综合分阈值用 Tailwind 颜色名（不是 v0.5 CSS 变量），UI spec 已显式映射（§4.1）但 Developer 实现时仍需对照映射表，否则颜色会偏离设计。
- **R2（中）**：本期新增 12-16 个 .vue 文件 + 7 个新 API endpoint，单纯 Developer 工程量约 v0.5 70% 体量；Tester 联调需要后端 mock 优先，spec 已假设契约可作 Tester 优先级排期参考。
- **R3（中）**：监控页角标 (§4.8) 计数口径**必然需要**包含本期 AC-32 新增告警类型，否则 Owner 看到角标 0 实际有 L0/L1 告警未处理 → 误以为系统正常 → 数据漏看。设计阶段必须由 Architect 同步定 AC-32 新增告警的 type 枚举（与 Architect #A2 闭环）。
- **R4（低）**：抽屉 480px 在移动端转 100% 全宽，断点 768px（v0.5 通用断点）；如 Owner 主要在桌面使用，可推后移动端适配优先级。
- **R5（中）**：v0.5 生产数据库已有 1000+ 行 `processed_news`（schema 是 `tags: string[]` + `importance_score: number`），v0.6 新增字段后渲染 v0.5 旧数据需要降级方式（Architect #A1 + Tester #T6 同源）。推荐方案：旧 `tags string[]` 全部归入 `processing` 类显示；`importance_score` 通过 API 层 alias 映射到 `score_total`（避免物理重命名 column）；新增字段 `translation / context / analysis / score_dimensions` 走"字段缺失隐藏"（AC-25c）—— Owner 看到 v0.5 历史新闻"只有标题 + 评分 + 处理类标签"是接受的降级形态。
- **R6（中）**：前端零自动化测试栈（无 vitest / playwright / @vue/test-utils），UI 类 AC（AC-22/AC-28/AC-29 等 12 条）验收手段沿用 v0.5 人工模式（Owner 浏览器手测 + Tester 旁观），本期不引入 Playwright/Storybook；如后续迭代决定引入工具化测试，单独立项（Tester #T1 闭环）。
- **R7（低）**：抽屉 6 段降级规则的「字段缺失」vs「字段为空」判定，统一采用 `v-if="!!field && (Array.isArray(field) ? field.length > 0 : true)"` 语义（即 `undefined / null / '' / [] / {}` 都算"缺失"，按 §3.2 第一档处理）—— mock fixture 和真实数据按此对齐（Tester #T2 闭环）。
- **R8（低）**：空间图标 `SpaceIcon` 静默回退在 onerror 触发时同步 `console.warn('[SpaceIcon] image load failed:', iconUrl)` + 在 wrapper element 上加 `data-fallback="emoji|default"` 数据属性，作为 Tester 可观测点；SpaceEditDialog 重打开时检测 `<img>` 加载失败需显示「ℹ️ 图片加载失败，请重新上传」提示，避免静默回退掩盖真实问题（Tester #T3 + Architect #A7 闭环）。
- **R9（低）**：上传交互态补 3 类异常场景细分（Tester #T4 闭环）：上传超时 30s 默认 → 「上传超时，请重试」+ 上传区重置；并发覆盖 → 「该图标已被另一处修改，请刷新页面后重试」不允许直接覆盖；断网 → 「网络已断开，恢复后请重新上传」不自动重试。

### 9.2 设计阶段需要 Architect 确认的事项

1. **NewsDetail 完整数据契约**：以 §7 + §6.1 已假设契约为基线，完成完整字段类型、ERD 与 schema 字段映射、序列化层 alias 规则。重点：`importance_score → score_total` 走 API 序列化 alias（推荐，避免 v0.5 53 测试改动）；`tags string[] → 分类对象` 历史数据降级（见 R5）；`translation / context / analysis / score_dimensions` 是落 `processed_news` 同表 jsonb 新列还是拆 `processed_news_l1_meta` 子表（Architect #A1）。
2. **SourceLevelStatusCounts API** 数据源：是基于 `tasks` 表还是 `raw_items + processed_news` join；4 字段语义明确每个 count 对应 L0/L1 哪一组合状态（Architect #A4）。
3. **全局 L0/L1 计数 API** (`/v1/level-status-counts`) 字段同 §6.4 但聚合所有 source；建议同时定义 `?source_id=:id` 参数实现单源/全源合并接口（Tester #T7）。
4. **图片上传 endpoint** (`POST /v1/spaces/icons/upload`) 路径、multipart 字段名、错误码规范；建议同时定 `DELETE /v1/spaces/:id/icon` 移除接口。
5. **旧 URL 兼容跳转**：放 Vue Router 内（推荐，无 SEO 影响）还是 nginx rewrite；选 Vue Router 时实现路径采用 `router.replace` 不入 history + query param `?tab=alerts|logs`（Developer #D9 + Tester #T5 闭环）。
6. **L1 手动重试资源粒度**：`POST /v1/l1-tasks/:task_id/retry`（任务粒度）vs `POST /v1/raw-items/:id/retry-l1`（信息粒度）二选一（Architect #A9）。
7. **AC-32 告警类型枚举值**：定 `task_stale / external_dep_down / task_backlog / final_failed_surge` 等具体 alerts.type；同步定告警阈值（如：连续 10 次 / 15 分钟内无新 completed / 1 小时内新增 ≥ 50 final_failed）—— 阈值建议设计阶段给 placeholder 而非完全留实施阶段（Architect #A17 + DevOps #O4 同源）。
8. **错误响应统一结构**：`NewsDetail` 接口的 error response 结构（`{ error: 'code' }` vs `{ error: { code, message } }`）由 Architect 在设计阶段统一定义（Tester #T11）。
9. **`SourceRecentNewsTimeline` 时间窗参数**：是否支持 24h/7d 切换 selector（推荐：v0.6 锁定 24h，后续按需扩展）；时间轴边界态（0 条 / 1 条 / >30 条）展示形态（Architect #A6 + Tester #T9）。
10. **角标轮询频率**：建议保持 60s（监控合并不改变告警生成频率）（Architect #A11）。
11. **空间图标分辨率上限**：补一句"图标推荐分辨率上限 512×512px；超出由后端 resize 或拒绝"（Architect #A19 + DevOps #O5）。
12. **AC-30 双表达落地**：监控页全局计数采用方案 A（MonitoringPage 加 GlobalLevelStatusCounts 组件 + 全局聚合 endpoint，已列入 §2.4 新建组件清单）；不走方案 B（"暂在 Source 详情页验收"）（Tester #T7 + Architect #A14 闭环）。

#### 高严重度（2 条）

**#A1（高）§6.1 / §7 NewsDetail 数据契约与 v0.5 现有 `processed_news` schema 字段名冲突，迁移路径未在 UI spec 标注**

- 关联：§6.1 `NewsDetail` 接口、§7 `GET /v1/news/:id`、PRD §3.4 评分和标签
- 现状：UI spec §6.1 定义的 `NewsDetail` 字段：
  - `score_total: number` —— 但 v0.5 `processed_news.importance_score numeric NOT NULL DEFAULT '0'`
  - `score_dimensions?: { timeliness/impact/confidence/clarity }` —— v0.5 schema 中无此字段
  - `translation?: { zh, original? }` —— v0.5 schema 中无
  - `context?: ContextParagraph[]` —— v0.5 schema 中无
  - `analysis?: string` —— v0.5 schema 中无
  - `tags?: { domain?, entity?, event?, content_type?, processing? }` —— v0.5 schema 现存 `tags jsonb`（结构是 `string[]`）+ `entities jsonb`（结构是 `any[]`）—— **结构不兼容**：v0.5 是平铺数组，v0.6 是分类对象
- 问题（架构师视角）：
  1. **`importance_score` → `score_total` 字段名变更**：是否物理重命名 column？还是 API 序列化层做 alias？前者影响 v0.5 53 个测试（AC-33 不回归），后者引入"DB 字段名 ≠ API 字段名"的长期债。
  2. **`tags` 从 `string[]` → 分类对象**：v0.5 历史数据（1000+ 行）的 `tags jsonb` 是 string[]，v0.6 读出来直接走分类对象会 crash。需要在 UI spec 标注"v0.5 历史数据如何展示"——降级到只显示在某一类（如 `processing`）？还是统一迁移成五类？
  3. **`context / translation / analysis / score_dimensions` 是新增字段**：是落在 `processed_news` 单表（新增 4 列 jsonb）还是拆 `processed_news_l1_meta` 单表？UI spec §7 没明确表结构变更的范围。
- 风险：Architect 设计阶段拿这一节实现，要面对"是改 5 个旧字段名还是加 5 个新字段并发期"+"v0.5 历史数据怎么办"两套决策。这是数据模型变更范围决策，本应在 UI spec 阶段说清楚（或显式标记"留给设计阶段"），不能只给 TS 类型让 Architect 反向推 DB schema。
- 修改建议：UI R2 在 §6.1 或 §9.2 加一段「v0.5 → v0.6 字段迁移策略」：
  - 显式列出 `importance_score`/`tags`/`entities` 三个 v0.5 现存字段是否保留、改名还是并存；
  - 显式列出新增字段（translation / context / analysis / score_dimensions）的承载方案候选（同表 jsonb 新列 / 拆 `processed_news_l1_meta` 子表 / 全量迁到 jsonb 单列）；
  - 显式标注"v0.5 历史数据"在 v0.6 UI 中的展示降级方式（如：旧 `tags string[]` → 全部归入 `processing` 类显示）。
- 如不在 UI R2 改，至少在 §9.2 设计阶段事项第 1 条「NewsDetail 完整数据契约」下展开为"§6.1 字段清单 + v0.5 现存字段迁移决策表 + v0.5 历史数据展示降级方式"三块，避免设计阶段拍脑袋。

**#A2（高）§4.8/§7 监控菜单角标数据源与 PRD R2 §3.7 AC-32 的告警类型扩展存在覆盖盲区**

- 关联：§4.8 监控菜单角标（D7）、§7 `GET /v1/alerts/count`、PRD R2 AC-32、UI spec §9.1 R3 风险段
- 现状：UI spec §4.8 + §7 写「角标数 = AlertsTab 未处理告警数（D7）」+「`GET /v1/alerts/count` 沿用 v0.5」，§9.1 R3 风险段也提了「如设计阶段决定告警来源也包括 L0/L1 final_failed 自动告警（AC-32），需更新角标计数口径」。
- 问题（架构师视角）：
  1. PRD R2 AC-32「外部依赖连续失败、L0/L1 队列长时间无进展、L1 final_failed 数量异常增长时，系统应产生**可见告警**或监控记录」—— "可见告警"按 v0.5 alerts 表语义就是建 `alerts` 记录。这是 PRD 已经定的需求，不是 R3 风险待评估事项。
  2. v0.5 `alerts.type` 现有枚举：`x_stream_disconnected / fetch_failure / zero_new / circuit_open` 等。v0.6 AC-32 隐含新增 3-4 种 type（`task_stale / external_dep_down / task_backlog / final_failed_surge` 或类似）—— 这是 schema 层扩展，UI spec §4.8 角标计数没说"是否包含本期新增告警类型"。
  3. 实际效果：如果 alerts 表新增 `task_stale` 类型，但 `GET /v1/alerts/count` 没更新查询条件，角标数会**漏 L0/L1 告警**。Owner 看到角标 0 实际有 3 条 L0/L1 告警未处理 → 误以为系统正常 → 数据漏看。
- 风险：UI spec §4.8 角标承诺与 PRD AC-32 告警生成承诺脱节，设计阶段如不主动收敛会出 bug。

**#T2（高）§3.2 抽屉 6 段降级规则区分「字段缺失」vs「字段为空」二分法，但 §6.1 NewsDetail 数据契约未对所有可选字段标注「缺失 vs 空」的判定方式，Tester 无法预制 mock fixture**

- 关联：§3.2、§6.1 NewsDetail 接口、PRD R2 AC-25c、Tester R2 复审 #T13（mock fixtures 产出归属未定）
- 现状：§3.2 写：
  - 「翻译 - 字段缺失时：隐藏整段 + 标记『未提供翻译』灰字」
  - 「翻译 - 字段为空时：同上」
  - 「背景补全 - 字段缺失时：隐藏整段」
  - 「背景补全 - 字段为空时：显示『本条暂无补全内容』灰字」
- 问题：「字段缺失」和「字段为空」是 JSON 序列化层的两个不同概念：
  - **字段缺失**：`{ title: '...', summary: '...' }`（无 translation key）→ `news.translation === undefined`
  - **字段为空**：
    - 字符串：`{ ..., translation: '' }` 或 `{ ..., translation: { zh: '', original: '' } }`
    - 对象：`{ ..., translation: null }` 或 `{ ..., translation: {} }`
    - 数组：`{ ..., context: [] }`
  - §6.1 `translation?: { zh: string; original?: string }` —— `?` 只表示 optional（可缺失），没说"空字符串"还是"null"对应"字段为空"
  - §6.1 `context?: ContextParagraph[]` —— 同样，`[]` vs `undefined` vs `null` 三种值在 §3.2 降级规则下行为可能不同
- Tester 视角问题：
  1. **mock fixture 怎么造**：测 AC-25c"字段缺失隐藏元素"，Tester 要造 mock 数据，但 spec 没说`undefined` `null` `''` `{}` `[]` 这 5 种值哪些算"缺失"、哪些算"为空"
  2. **断言怎么写**：测 §3.2 背景补全规则，"字段缺失隐藏整段"和"字段为空显示灰字"，Tester 必须能区分这两种 mock 数据 → 但前端 Vue 模板里 `v-if` `v-show` `Array.length === 0` 对这 5 种值的行为不一致
  3. **联调时后端实际返回什么**：如果后端走"未生成则字段不返回"（缺失），Tester 测试用例和实际行为对齐；如果后端走"未生成则返回 null"（为空），UI 该走"隐藏"还是"显示灰字"会有偏差
- 风险：mock fixture 与真实数据不一致 → 测试通过但生产环境降级行为错乱
- 修改建议：UI R2 在 §3.2 表头或 §6.1 NewsDetail 加一段"字段缺失 vs 字段为空判定规则"：
  - 推荐方案：统一以「`v-if="!!field && field.length > 0"`」语义判定（即 `undefined / null / '' / [] / {}` 都算"缺失"，按§3.2 第一档处理；只有非空字符串/非空数组/非空对象才算"有内容"）
  - 然后把 §3.2 表合并为 1 列「字段无值（缺失/null/空）时」+ 「字段有内容时」二态
  - 或：保留二分法但显式定义"字段缺失 = key 不存在 OR null OR undefined；字段为空 = '' OR [] OR {}"
- 优先级：高。这条不修订会让 Tester 测试 AC-25c 时反复返工，且 v0.6 实施完成后生产环境降级行为可能与 UI 设计不符。

- 优先级：高。AC-28 / AC-28a 测试用例无法精确断言会让"图标加载失败回退"成为 v0.6 一个长期黑盒。
