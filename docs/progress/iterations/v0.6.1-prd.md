## 1. 迭代目标

v0.6.1 聚焦一件事：**将 xiaobao 与 AI 中枢的集成模式从 HTTP 同步调用改为数据库契约边界异步解耦，并将翻译前置为 xiaobao 侧独立步骤**。

背景：v0.6 上线了 AI 处理能力（默认关闭），采用 HTTP 同步调用模式，单条处理耗时 74~79 秒，调用方需挂起等待，且重试、超时、解耦能力弱。v0.6.1 将集成模式改为"xiaobao 入库标记状态 → AI 轮询取数处理 → 写回数据库 → xiaobao 前端按状态展示"，天然解决异步、重试、超时解耦问题。

核心产品决策：**翻译前置到 xiaobao 侧**，作为 L0 过滤之后、AI 深度解析之前的独立步骤。英文新闻先翻译再入库展示，用户先"看得懂"，再等 AI"加工得更有价值"。翻译是阅读基础门槛，不是附加值。

同时配套产品更正：新闻分两类（AI 处理类 vs 直显类），前端按处理状态区分展示层级（富展示 vs 基础展示），保证内容不积压丢失。

一句话目标：

> xiaobao 与 AI 中枢以数据库为契约边界解耦，翻译前置（xiaobao 侧）+ AI 深度解析异步化（ai 侧），前端按处理状态分层展示，建立两阶段渐进增强的 AI 集成底座。

## 2. 用户故事

### 2.1 英文新闻先翻译再阅读

**作为** 中文用户，**我想** 英文新闻抓取后先自动翻译成中文再展示，**以便** 我不需要依赖翻译工具就能看懂外文新闻。

### 2.2 异步 AI 处理不阻塞基础阅读

**作为** 平台用户，**我想** 新闻抓取后先入库展示、AI 在后台异步深度解析，**以便** 不需要等 AI 处理完就能看到内容，处理完成后自动升级展示。

### 2.3 处理状态可视化

**作为** 平台用户，**我想** 在新闻卡片和详情抽屉里直观看到这条新闻的处理进度（翻译中 / 解析中 / 已完成 / 失败），**以便** 理解内容丰富度差异，知道哪些新闻还在加工中。

### 2.4 直显类新闻不丢失

**作为** 平台用户，**我想** 第一类新闻（不需要 AI 深度解析的直显类）能正常展示，**以便** 即使 AI 处理速度跟不上抓取速度，页面内容也不会积压骤减。

### 2.5 AI 故障不影响基础浏览

**作为** 平台用户，**我想** AI 服务挂了的时候我照样能看新闻（包括已翻译的外文新闻），**以便** AI 链路故障不影响基础浏览体验。

### 2.6 管理侧可观测全链路状态

**作为** 平台管理员，**我想** 在管理/监控页看到翻译队列、AI 解析队列、成功/失败统计、卡住的任务，**以便** 掌握全链路健康状况，必要时手动干预。

## 3. 验收标准

### AC-01：L0 过滤后立即展示（基础展示）
当一条新闻抓取并通过 L0 过滤后，应立即可以在前端以基础展示形态看到，不需要等待翻译或 AI 处理完成。L0 未通过的新闻不展示。

### AC-02：英文新闻自动翻译
当一条新闻通过 L0 过滤且检测为非中文时，xiaobao 应自动发起翻译；翻译完成后前端展示翻译后的内容，无需用户手动操作。中文新闻直接进入下一阶段。

### AC-03：翻译失败不阻塞展示
翻译失败时，新闻应展示原始内容，并标记「翻译失败」；翻译失败不影响后续 AI 深度解析（可以基于原文做解析）。

### AC-04：AI 深度解析完成后自动升级展示
当 AI 深度解析完成并写回结果后，前端展示应自动升级为富展示形态（评分 / 摘要 / 标签 / 上下文），刷新后可见即可（不强求实时推送）。

### AC-05：多阶段状态可视化
新闻卡片和详情抽屉中应有明确的处理状态指示，至少区分：等待翻译、翻译中、等待 AI 解析、AI 解析中、已完成、处理失败六种状态。

### AC-06：直显类新闻正常展示
第一类新闻（直显类，不经 AI 深度解析）应能正常入库并展示，展示形态与 v0.5/v0.6 现有基础展示一致。

### AC-07：AI 服务故障不影响基础链路
当 AI 服务不可用时，xiaobao 的抓取、L0 过滤、翻译、基础展示链路应完全不受影响；已标记为待 AI 处理的新闻保持待处理状态，不报错、不丢数据。

### AC-08：状态机完整覆盖正常与失败路径
AI 类型新闻的状态机至少包含：待翻译、翻译中、翻译失败、待 AI 处理、AI 处理中、AI 处理成功、AI 可重试失败、AI 最终失败八种稳定状态；状态转移合法，不允许非法跳转。

### AC-09：处理中卡死可回收
处于「翻译中」或「AI 处理中」状态的任务如果超过设定时间阈值仍未更新，应能被回收为对应等待状态重新进入队列，避免卡单。

### AC-10：重试次数限制
AI 深度解析失败且可重试的任务，重试次数达到上限后应标记为最终失败，不再无限重试。

### AC-11：共享库 schema 权属
ai 服务只能读取指定的待处理数据、写回指定的结果字段，不能创建表、修改表结构或读取超出契约范围的数据。翻译相关表和字段完全由 xiaobao 管理，ai 不接触翻译逻辑。

### AC-12：ai 侧适配层封装
ai 侧的数据获取逻辑应封装为独立的数据源适配层，AI 处理核心不感知数据是从数据库来还是从 HTTP 请求来，保留未来接入其他调用方的能力。

### AC-13：管理侧全链路统计
管理/监控页应能看到全链路处理统计：翻译队列长度、翻译今日成功/失败、AI 待处理数量、AI 处理中数量、AI 今日成功/失败、最终失败数。

### AC-14：现有抓取链路不回归
RSS / X Stream / 其他 Source 的抓取链路、L0 过滤逻辑、直显类新闻展示行为与 v0.6 相比不发生功能回归。

### AC-15：契约变更走程序
本迭代上线前，coordination 仓的 `contracts/` 下应有数据库边界契约（表、字段、状态枚举、读写权属），`CHANGELOG.md` 有对应记录；ai 侧改造有对应 REQ 提报并被承接。

### AC-16：灰度切换能力
应支持在 HTTP 模式和数据库模式之间切换 AI 深度解析的集成方式（通过配置开关），便于灰度验证和回滚。翻译功能始终在 xiaobao 侧，不受此开关影响。

## 4. 范围边界

### 本迭代做

1. **集成模式切换**：xiaobao 与 AI 中枢从 HTTP 同步调用改为数据库契约边界异步解耦（仅 AI 深度解析部分）
2. **翻译前置（xiaobao 侧）**：L0 过滤后自动检测语言，非中文自动翻译；翻译在 xiaobao 侧完成，作为独立步骤，调用第三方翻译 API
3. **三层入库架构**：原文层（raw_items）→ 翻译层（translations 新表）→ AI 解析层（processed_news），每层独立存储、独立状态机、独立失败重试
4. **两阶段状态机**：翻译阶段（待翻译 / 翻译中 / 翻译失败）+ AI 解析阶段（待 AI / 处理中 / 成功 / 可重试失败 / 最终失败）+ 卡死回收机制
5. **处理类型区分**：引入「处理类型」字段（direct / ai），直显类新闻不进 AI 状态机
6. **前端展示分层**：按处理状态区分展示层级——富展示（AI 已解析）vs 基础展示（翻译中 / 翻译完成待解析 / 直显 / 失败）
7. **管理侧全链路统计**：监控页补充翻译队列 + AI 解析队列和统计概览
8. **灰度切换开关**：支持 HTTP 模式与数据库模式切换 AI 深度解析的集成方式（翻译不受影响）

### 本迭代不做

1. **实时 WebSocket 推送**：前端不做处理完成的实时推送，刷新后看到更新即可
2. **AI 处理质量优化**：不优化 L1 处理的算法、prompt、评分质量，本期只改集成模式
3. **多调用方真实化**：ai 侧只做适配层封装，不实现第二个真实调用方
4. **L0 算法改造**：L0 过滤逻辑不变，仍由 xiaobao 负责
5. **新的 AI 能力类型**：本期只做 news-l1 一类 AI 任务的迁移，不新增其他 AI 任务类型
6. **原始数据治理**：不做原始信息的归档、清理、保留周期配置
7. **前端管理页大改版**：只在现有监控页基础上补充统计，不重做管理界面
8. **翻译质量优化**：翻译只做基础能力接入，不做翻译模型选型优化、术语库、翻译记忆等
9. **多语言翻译**：本期只支持外文 → 中文翻译，不支持中文 → 外文或其他语言对

## 5. 界面要点（PM 兼 UI）

### 5.1 整体原则
- 本期 UI 变更以**两阶段渐进增强**为核心：翻译是第一阶段（先"看得懂"），AI 深度解析是第二阶段（再"有价值"）
- 不新增页面、不大改布局，核心交互保持与 v0.6 一致
- 处理状态是**渐进增强**信息，不喧宾夺主
- L0 过滤掉的新闻（广告/无效信息）**不展示**，不进入用户视野

### 5.2 两阶段处理流程总览

```
抓取 → L0 过滤（无效的丢弃） → 翻译检测
                              ├─ 中文 → 直接入库，进入 AI 队列 → 基础展示（标题+原文）→ AI 深度解析 → 富展示
                              └─ 外文 → 翻译中 → 翻译完成 → 入库，进入 AI 队列 → 基础展示（标题+译文）→ AI 深度解析 → 富展示
                                                    ↓
                                                翻译失败 → 入库，展示原文 + 「翻译失败」标记 → 仍可进入 AI 队列
```

### 5.3 新闻卡片展示分层

**富展示态（AI 深度解析完成）**：
- 标题（中文）+ AI 摘要 + 四维评分徽章 + 领域/实体标签
- 与 v0.6 L1 处理完成后的卡片展示一致
- 状态徽章：无额外徽章（默认就是富展示态）

**基础展示态（翻译中 / 翻译完成待 AI / 直显类 / 处理失败）**：
- 标题 + 内容预览（截断）
- 不展示评分、不展示 AI 摘要、不展示标签
- 内容预览的语言取决于翻译状态：
  - 翻译中：显示原文预览 +「翻译中」角标
  - 翻译完成待 AI：显示译文预览 +「解析中」角标
  - 直显类：显示原文/译文预览 + 无角标
  - AI 处理失败：显示译文（或原文）预览 +「解析失败」低调标记

### 5.4 卡片状态徽章设计

| 状态 | 卡片角标 | 位置 | 视觉风格 |
|------|---------|------|---------|
| 翻译中 | 「翻译中」 | 卡片右上角 | 蓝色系，小型 badge，轻微脉冲动画 |
| AI 解析中 | 「解析中」 | 卡片右上角 | 蓝色系，小型 badge，轻微脉冲动画 |
| 翻译失败 | 「翻译失败」 | 卡片底部小字 | 灰色，低调，hover 可看原因 |
| AI 解析失败 | 「解析失败」 | 卡片底部小字 | 灰色，低调，hover 可看原因 |
| 已完成（富展示） | 无 | — | — |
| 直显类 | 无 | — | — |

约束：
- 状态角标不占用卡片核心内容区域
- 动画应克制，不干扰阅读流
- 失败态默认低调，hover 才展示失败原因摘要
- 「翻译中」和「解析中」不能同时出现（同一时刻只显示当前阶段）

### 5.5 抽屉（详情页）展示分层

抽屉内信息密度更高，按处理阶段展示对应内容：

**AI 已解析（富展示态）**：
- 四段式完整展示：标题 / AI 摘要 / 翻译 / 评分+标签 / 上下文+分析
- 与 v0.6 L1 完成态一致

**翻译完成、AI 待解析 / 解析中**：
- 顶部：标题（翻译后的中文标题）
- 主体：翻译全文 +「AI 深度解析中，预计 1~2 分钟完成」进度提示
- 底部：状态条显示当前阶段（「✓ L0 通过 · ✓ 翻译完成 · ⏳ AI 解析中」）
- 右侧或底部显示原始链接/来源信息

**翻译中**：
- 顶部：原文标题
- 主体：原文内容 +「翻译中...」加载动画
- 底部：状态条（「✓ L0 通过 · ⏳ 翻译中 · ○ AI 待解析」）
- 用户可以先读原文，等翻译完成后自动切换

**AI 解析失败**：
- 顶部：标题
- 主体：翻译全文（或原文）
- 底部：状态条（「✓ L0 通过 · ✓ 翻译完成 · ✕ AI 解析失败」）+ 失败原因摘要
- 不展示评分/标签/摘要

**直显类**：
- 标题 + 全文内容（翻译后的）
- 无处理状态条
- 与 v0.5/v0.6 直显态一致

### 5.6 状态条设计（抽屉内）

状态条显示完整处理链路，已完成的打勾、进行中的动画、未开始的置灰：

```
✓ L0 通过  →  ✓ 翻译完成  →  ⏳ AI 解析中  →  ○ 已完成
```

- 直显类新闻不展示状态条
- 失败态用 ✕ 标记失败阶段，后续阶段置灰
- 状态条位于抽屉底部或顶部，不占主体阅读区域

### 5.7 监控页全链路统计模块

在现有监控页增加「AI 处理概览」区块，分两段展示：

**翻译段**：
- 待翻译数量
- 翻译中数量
- 今日翻译成功数
- 今日翻译失败数

**AI 解析段**：
- 待解析数量
- 解析中数量
- 今日解析成功数
- 今日解析失败数（可重试 + 最终失败分开）
- 最终失败累计数

展示形式：数字卡片网格，与现有告警/日志统计风格一致。

### 5.8 用户流程映射

**浏览新闻流程**：
1. 用户进入浏览页 → 看到新闻流（富展示 + 基础展示混排，按时间排序）
2. 外文新闻先显示「翻译中」→ 翻译完自动切换为译文 +「解析中」
3. AI 解析完后刷新页面可看到富展示态
4. 点击卡片看详情抽屉

**详情阅读流程**：
1. 点击卡片打开抽屉
2. 抽屉内展示对应状态的内容（翻译中 / 解析中 / 已完成）
3. 底部状态条显示当前处理进度
4. 关闭抽屉返回列表

**管理侧监控流程**（新增）：
1. 管理员进入监控页
2. 看到翻译段 + AI 解析段的全链路统计
3. 发现异常（如队列积压、失败率高）→ 进一步排查

### 5.9 空状态与错误状态

- AI 服务不可用时：浏览页不受影响，监控页 AI 解析区块标注「AI 服务不可用」
- 翻译服务不可用时：外文新闻显示原文 +「翻译暂不可用」标记，仍可进入 AI 解析队列
- 全部新闻都已处理：监控页统计正常显示，不做空态

## 7. 风险和开放问题

### 风险

1. **AI 处理速度跟不上抓取速度**：单条约 74~79 秒，理论日上限约 1100 条。如果抓取量超过处理速度，待处理队列会持续增长。
   - 缓解：直显类新闻不进 AI 队列；前端基础展示保证内容不丢失；监控页可观测队列长度。
   - 后续：评估并行度提升、优先级队列、批量处理等优化方向。

2. **共享库 schema 变更不同步**：xiaobao 改 schema 后 ai 侧可能未及时适配。
   - 缓解：契约文件作为真源，变更走 coordination 流程；schema 权属明确归 xiaobao。

3. **卡死回收误判**：超时阈值设置不当可能导致正常处理中的任务被错误回收，引发重复处理。
   - 缓解：超时阈值留充足余量（如 10 分钟）；处理中状态定期心跳更新；回收前校验最后活跃时间。

4. **前端刷新才能看到更新**：AI 处理完成后用户不刷新页面就看不到富展示。
   - 缓解：本期接受此限制（异步处理本身就有延迟）；后续可考虑轮询或 WebSocket 推送。

### 开放问题

1. **直显类 vs AI 类的划分规则**：哪些新闻走 direct、哪些走 ai，本期 PRD 只定义两类的存在和展示差异，具体划分规则待后续迭代明确（v0.6.1 可先按 Source 类型或空间配置简单区分，或全部走 ai + 直显兜底）。

2. **轮询间隔与单次取数上限**：待设计阶段确定，参考值：轮询间隔 5~10 秒，单次取数上限 5~10 条。

3. **卡死回收超时阈值**：待设计阶段确定，参考值：翻译 5 分钟，AI 解析 10 分钟。

4. **重试次数上限**：待设计阶段确定，参考值：翻译 2 次，AI 解析 3 次。

5. **灰度切换策略**：是先上数据库模式、保留 HTTP 作为回滚选项，还是两边并行一段时间？待 DevOps Review 后确定。

6. **processed_news 与 news_positions 的写回职责**：AI 处理完成后，processed_news 写入和 news_positions 关联由谁负责？是 ai 直接写，还是 xiaobao 收到完成信号后写？待设计阶段明确（影响契约边界）。

7. **translations 表结构设计**：三层入库架构中的翻译层表结构（字段、索引、与 raw_items 的关联方式、翻译状态字段）待 Architect 在设计阶段细化。

8. **翻译 API 选型**：第三方翻译 API 的具体选型（DeepL / 腾讯翻译君 / 有道 / 百度翻译等）待设计阶段确定，参考标准：速度、成本、稳定性、中文翻译质量。

9. **现有 processed_news.translation 字段的处理**：新增 translations 表后，现有 processed_news 表的 translation 字段是迁移过去还是保留作为冗余？待 Architect 评估迁移成本。
